What Is GENESIS? The Simple Explanation
No jargon. No assumptions about technical background.

Imagine you own a large office building and you want to test how secure it is. You could hire a single security guard to walk around and check that all the doors are locked. That is what a traditional security scanner does — it checks known locks against a list of known problems.

GENESIS is different. Instead of one guard with a checklist, GENESIS sends in a team of specialized investigators who each have deep expertise, think independently, argue with each other about what they find, verify every claim before reporting it, and write a full brief that tells you exactly how a real attacker could break in and what to do about it.

Analogy — The Forensic Investigation Team

Think of GENESIS like hiring an entire forensic investigation firm rather than a security guard. One investigator focuses on the building's external footprint (reconnaissance). Another specializes in door-lock mechanisms (authentication). A third is an expert in hidden passages (code analysis). A fourth tries to argue that every proposed risk is exaggerated, forcing the team to prove their claims (adversarial debate). Nothing gets reported as a confirmed finding until the evidence has been tested and verified. The final report tells you not just what is broken, but proves it is broken, explains how a thief would exploit it step by step, and tells you exactly how to fix it.

How GENESIS Differs From Regular Security Scanners
Understanding the gap between checking boxes and thinking through attacks.

❌ Traditional / Automated Scanners

  • Run a fixed list of pre-programmed checks
  • Match patterns against a known-vulnerability database
  • Report everything that might be an issue (many false positives)
  • Cannot connect multiple small issues into one big attack chain
  • Finish when the checklist is done
  • Cannot adapt to your specific application's technology
  • Cannot form hypotheses or reason about novel vulnerabilities
  • Produce reports that require weeks of human expert review to validate

✅ GENESIS

  • Dynamically plans which checks to run based on what it discovers
  • Forms its own hypotheses about what might be broken and why
  • Only reports what it has actually proven (near-zero false positives)
  • Assembles chains showing how attackers could combine issues for bigger impact
  • Continues iterating until coverage goals are met, not until a timer stops
  • Activates specialist agents based on your specific technology stack
  • Discovers novel vulnerabilities not in any database
  • Delivers validated, immediately actionable findings
Analogy — The Doctor vs. The Checklist

A traditional scanner is like a receptionist with a checklist: "Do you have a fever? Yes or no. Do you have a cough? Yes or no." It runs through a fixed set of questions and flags anything that matches. GENESIS is like a senior physician: it listens, forms a diagnosis, orders targeted tests to confirm it, and only tells you what it has ruled in — not everything it might have considered and ruled out.

The Key Differentiator: GENESIS Does Not Scan — It Investigates

Most tools are scanners — they run automated checks. GENESIS is an investigator — it reasons about attack scenarios, selects the right tools for each scenario, tests its hypotheses, refines them based on what it finds, and builds a case from evidence. This is fundamentally different from running a tool against a list of known vulnerabilities.

The "Thinking" Difference: After finding a login page, a traditional scanner checks: "Does it have default passwords? Does it lock out after 10 tries?" GENESIS asks: "What is this login page built with? What is the trust model? If I forge a token with the wrong algorithm, does it still accept me? If I chain this login weakness with that database call I saw earlier, can I reach customer data?" — and then it actually tries.

The GENESIS Scan Journey — Step by Step
Everything that happens from the moment you press "Start Scan" to the final report.
1

Scan Initiation — Setting the Mission

When you start a GENESIS scan, you provide a target (an IP address or web application URL) and a scan mode: Standard, Deep Research, or Exhaustive. These modes control how long GENESIS spends and how deeply it digs. Deep Research runs for at least 6 hours of active investigation. Exhaustive runs until every avenue has been explored.

GENESIS immediately creates a session — a unique workspace that tracks every decision, every tool run, every hypothesis, and every finding for this particular investigation. Think of it as opening a case file. A background task manager (called Celery) picks up this case file and begins the investigation process.

Analogy

Like a detective agency opening a new case. The case number is assigned, the client brief is logged, the investigators are briefed on scope, and the clock starts.

2

Goal Setting — What Does Success Look Like?

Before doing anything, GENESIS defines its investigation goals. These goals are specific, testable questions such as: "Have we tested all authentication endpoints?", "Have we checked all places where user data is passed to the database?", "Have we mapped all the ways an unauthenticated user can trigger privileged operations?"

These goals are tracked in a live progress system. A goal can be: pending, in progress, or complete. GENESIS does not consider its investigation done until every goal reaches "complete." This prevents the shallow coverage that plagues time-limited automated scans.

3

Reconnaissance Phase — Getting to Know the Target

Two specialist agents run in parallel at the start: the Recon Agent and the Analyst Agent. Together, they build a complete picture of what they are dealing with.

The Recon Agent finds all the doors and windows — what ports are open, what services are running, what subdomains exist, what the network looks like from the outside. The Analyst Agent interprets what those findings mean — what technology is being used, what known weaknesses that technology has, whether there are protective shields like a firewall in place.

Coverage gate: Neither agent is allowed to finish this phase until it has used at least 5 different investigation tools and has made at least 3 meaningful discoveries. This prevents a "quick look" that misses critical context.

Analogy

Like a building surveyor walking the exterior before any internal inspection begins. They map every entrance, note the security cameras, check what alarm system is installed, and photograph the surroundings before anyone tries a single door handle.

4

Hypothesis Formation — What Could Be Wrong and Why?

Based on what reconnaissance found, GENESIS forms hypotheses — educated guesses about specific security weaknesses. A hypothesis is not a finding — it is a structured proposition: "I believe the login endpoint may accept tokens with a forged signature because the code relies on a hand-rolled verification function that does not check the algorithm header." Each hypothesis has a confidence score (0 to 1), a list of evidence that supports it, and a proposed way to test it.

These hypotheses are managed in a Hypothesis Market — a live tracking system where each hypothesis's confidence rises when more evidence supports it and falls when evidence contradicts it. Only hypotheses that reach a high enough confidence score trigger dedicated testing.

5

Specialist Activation — Assembling the Right Team

Based on what was found in reconnaissance, GENESIS activates the right specialist investigators. If the target uses a web application with a login system, the authentication specialist wakes up. If source code is available, the code analysis specialist is added. If the application handles cryptography (encryption, digital signatures), the cryptography specialist joins. If the target is an industrial control system, the OT/IoT specialist is activated.

Up to 8 specialist agents can run simultaneously in addition to 3 always-active generalist agents (exploit, code, payload). This creates a coordinated team of up to 11 investigators working on the same target at the same time.

6

Investigation Rounds — The Iterative Discovery Loop

Agents work in rounds. Each round, agents take their hypotheses, select the right tools, run them, read the results, update their understanding, and propose new hypotheses based on what they found. Findings that one agent discovers are immediately shared with all other agents in the same session so no team member misses relevant information.

After each round, a Session Judge — a senior oversight agent — reviews what has been covered and what has been missed. It issues specific directives: "The authentication team has not tested token expiry. Prioritize that next round." These directives are injected directly into the agents' next-round instructions.

The loop continues until: all goals are complete, minimum time thresholds are met, and coverage benchmarks are achieved. This is not time-based termination — it is goal-based termination.

7

Adversarial Debate — Testing Every Claim

When an agent proposes a high-confidence finding, it does not go straight to the report. Instead, it goes into a structured debate between a Red Agent (the attacker who proposes and defends the finding) and a Blue Agent (the defender who challenges every aspect of it). This is called the Red-Blue Dialectic. The debate runs for up to 3 rounds. If the Red Agent's case survives the Blue challenge, the finding's confidence is boosted. If it does not survive, the confidence is reduced and the finding may be reclassified.

8

Proof Validation — From Theory to Evidence

Every surviving finding must be proven. GENESIS executes a specific, targeted test against your live system to confirm the vulnerability is actually exploitable. For example, if the finding is "SQL injection on the search endpoint," GENESIS actually sends a carefully crafted safe input to that endpoint and checks whether the response confirms that the database query was manipulated. It does not assume — it tests.

Only findings that pass this proof test are promoted to confirmed vulnerabilities. Everything else remains a candidate that requires further investigation or is discarded. This is the foundation of GENESIS's near-zero false positive rate.

9

Chain Assembly — Finding the Big Picture

Individual confirmed vulnerabilities are fed into a knowledge graph — a map that shows how different findings connect. GENESIS looks for chains: can vulnerability A be used to gain access that then makes vulnerability B exploitable? Can combining three medium-severity issues produce a critical-severity attack path? These chains are assembled and scored. The highest-severity chains appear prominently in the final report as end-to-end attack scenarios.

10

Reporting — The Final Brief

The final output includes: every confirmed vulnerability with its proof evidence, severity rating (Critical / High / Medium / Low), risk description in plain English, mapped attack technique codes (MITRE ATT&CK), and specific step-by-step remediation instructions. Attack chains that link multiple findings are presented as complete scenarios so leadership can understand not just individual issues, but the full business impact of leaving them unresolved.

The Agents — Who Does What
Every agent in GENESIS has a specific role, a specific set of tools, and specific rules about when it can claim its work is done.

Phase 1 Agents — Always Active at Scan Start

Reconnaissance

Recon Agent

Maps the external attack surface. Finds open ports, services, subdomains, DNS records, and any publicly visible infrastructure. Must complete 5 tool calls and make 3 meaningful topology discoveries before it is allowed to finish.

Analysis

Analyst Agent

Identifies what technologies are in use, whether security shields (WAFs, TLS) are present, what CMS or framework powers the application, and what known weaknesses exist in those technologies. Must emit 3 hypotheses before finishing.

Phase 2 Agents — Always Active During Investigation

Generalist — Attack

Exploit Agent

The primary hands-on attacker. Tests all discovered endpoints with relevant attack payloads. Runs vulnerability scanners, injection testers, authentication bypass tools, and business logic checks.

Generalist — Code

Code Agent

Analyses application source code or compiled binaries when available. Looks for dangerous patterns: unsanitized inputs, hardcoded secrets, insecure cryptographic implementations, missing ownership checks.

Generalist — Payload

Payload Agent

Creative payload specialist. Invents novel attack inputs that go beyond standard vulnerability scanner payloads. Designed to find the unexpected — uses a less-restrictive AI model configuration for maximum creative latitude.

Specialist Agents — Activated by Signal

These agents are only brought into the investigation when Phase 1 detects evidence that their expertise is needed. A maximum of 8 specialists run per session.

Specialist

Authentication Agent

Deep expertise in login systems, JWT tokens, OAuth flows, SAML assertions, session management, and password reset flows. Active whenever an authentication mechanism is detected.

Specialist

Cryptography Agent

Tests cryptographic implementations for mathematical weaknesses — weak random number generation, padding oracle attacks, algorithm confusion, hardcoded keys. Active when any encryption or signing mechanism is found.

Specialist

Network Agent

Tests for HTTP request smuggling, SSRF (making the server fetch internal resources), CORS misconfigurations, and other network-layer vulnerabilities.

Specialist

Reverse Engineering Agent

Decompiles binary files and firmware to extract logic, hardcoded credentials, and vulnerabilities that are invisible from the outside. Active when compiled binaries are available.

Specialist

Exploit Development Agent

Crafts full working exploits for confirmed vulnerabilities. Assembles Return-Oriented Programming chains for binary exploitation. Active for high-severity findings that warrant full proof-of-concept construction.

Specialist

Source Analyst / Invariant Engineer

Analyses large codebases, infers what the code is supposed to do, and identifies gaps between the intended security model and the actual implementation. Can process files exceeding 100,000 lines of code.

Specialist

IoT / OT / Embedded Agent

Activated when industrial control systems, embedded devices, or Internet-of-Things hardware are detected. Has specialist tools for these environments which have fundamentally different threat models from web applications.

Specialist

Mobile Agent

Assesses mobile application backends and APIs. Active when mobile-specific API patterns or mobile app artifacts are detected.

Oversight and Reasoning Agents

Strategic Oversight

Session Judge

After each investigation round, the Session Judge reviews all findings, all coverage gaps, and all incomplete goals. It issues written directives to the specialist agents telling them exactly what to prioritise next. It also decides when the investigation is thorough enough to proceed to validation.

Strategic Oversight

Session Supervisor

Monitors the overall session for coverage drift — situations where the team has been spending too much time on one area while ignoring others. Injects corrective instructions at the beginning of each agent's next turn.

Philosophy

Philosopher Agent

Activated after Round 1. Takes all the anomalies and partial observations the team has gathered and asks: "What deeper bug class would explain all of these observations together?" It proposes 3–5 novel hypotheses that no individual agent would have arrived at alone. This is how GENESIS finds zero-day vulnerabilities.

Adversarial

Red Agent (Attacker Persona)

Proposes and defends security hypotheses. Takes the role of a motivated attacker who believes the vulnerability is real and exploitable. In debate, it argues for why the finding matters and how it would be exploited.

Adversarial

Blue Agent (Defender Persona)

Challenges every hypothesis with counter-arguments: "But the WAF would block that payload." "But you need valid credentials first." "But that code path is never called in production." Forces the Red Agent to prove its case is genuinely exploitable.

Threat Persona

Insider Threat & Nation State Agents

Specialized attacker personas for advanced threat modelling. The Insider Threat agent thinks like a malicious employee with legitimate access. The Nation State agent thinks like a well-resourced, patient adversary willing to spend weeks on a target.

How Agents Share Information

All agents in the same session share findings in real time via a shared memory channel (Redis). When the Exploit Agent discovers that a login endpoint accepts any algorithm type on its security tokens, it immediately publishes that finding. The Authentication Agent reads it within seconds and re-orients its next round of tests to focus on token-based attacks. The Code Agent reads it and starts looking for the specific function in the source code that handles token verification. This coordination is continuous and automatic — no human has to copy findings from one team member to another.

Tools & MCP Servers — The Scanner's Toolkit
Over 50 industry-standard and custom security tools, all orchestrated through a unified interface.

Agents do not run attacks themselves — they direct tools to do so. GENESIS uses a standardised connection layer called MCP (Model Context Protocol) that allows AI agents to call any security tool using a consistent interface, regardless of whether that tool is a commercial scanner, an open-source utility, or a custom-built GENESIS capability.

Analogy — The Universal Remote

MCP is like a universal remote control for security tools. Instead of each agent needing to know how to operate 50 different tools with 50 different interfaces, every agent uses the same "channel up / channel down" controls, and MCP translates those into the correct instructions for each specific tool behind the scenes.

Adversarial Thinking — Red vs. Blue Debate
How GENESIS challenges its own conclusions before trusting them.
Analogy — The Devil's Advocate

In a law firm, before a case is filed, a senior partner plays devil's advocate — they argue the opposition's strongest possible case to find the weaknesses in the planned argument. GENESIS does exactly this for every high-confidence security finding. One AI argues the finding is real and dangerous. Another AI argues it is not. The finding only survives if the attacker's case is strong enough to withstand serious challenge.

The Red-Blue Dialectic

R

Round 1 — Red Proposes

The Red Agent presents the attack hypothesis: what the vulnerability is, how it would be exploited, what the impact would be, and what evidence supports it. It sets a confidence stake — how strongly it believes in the finding.

B

Round 2 — Blue Challenges

The Blue Agent responds with the strongest possible counter-arguments: "The firewall blocks that request." "The application validates input before it reaches that function." "You need to be authenticated first, which requires bypassing a separate control." "The token you're describing would be rejected by the server."

R

Round 3 — Red Defends or Concedes

Red either successfully addresses Blue's challenges (increasing confidence) or concedes that the finding is weaker than initially thought (decreasing its confidence stake by 0.3). This back-and-forth can run up to 3 debate rounds. The full transcript is saved for audit.

The Philosopher Agent — Finding What Nobody Looked For

After the first investigation round, the Philosopher Agent reads all the partial observations, anomalies, and unexpected results from every agent's work. It then performs a different kind of reasoning: "What class of bug would explain all these observations together, even if no single observation proves it?" It then proposes 3–5 novel hypotheses that represent attack scenarios no standard tool would have found.

Real Example: Three agents independently noticed that (1) the token endpoint accepts unusual algorithm headers, (2) the source code shows a hand-written verification function, and (3) the application uses an older version of a cryptographic library. The Philosopher Agent combines these three observations into a single hypothesis: "The hand-written verifier may be susceptible to algorithm substitution attacks where a legitimate signature under one algorithm can be repurposed to forge signatures under another." This is a class of vulnerability that would not appear in any standard scanning checklist.

Cross-Model Validation (Independent Second Opinion)

For the highest-stakes findings, GENESIS can invoke a completely different AI model family to review the Red Agent's case. When two independent AI models — trained differently, by different organisations — both agree that a finding is valid, the confidence score receives an additional boost. This is equivalent to getting a second medical opinion from a doctor at a different hospital using different training and methods.

Reasoning Loops — How GENESIS Thinks Through Hard Problems
A structured cycle of ticks, branches, and chosen paths that replaces single-step guessing with disciplined step-by-step investigation.

What Is a Reasoning Loop?

A reasoning loop is a structured way for the AI to think through a hard problem in smaller, disciplined steps rather than jumping straight to a conclusion. Instead of asking one big question and hoping for the right answer, GENESIS breaks the thinking into a repeating cycle:

Analogy — The Detective at the Whiteboard

Imagine a detective standing at a whiteboard with three columns: What I know now, What could be true from here, and The path I will follow next. At each step, the detective writes down the current situation, draws every possible next move on the board, scores each move by how likely it is to reveal the truth, picks the best one, takes that action, then comes back and updates the board. This cycle repeats until the case is solved or conclusively closed. That cycle — observe, branch, choose, act, return — is a reasoning loop.

The Three Core Mechanics: Tick, Branch, Chosen Path

⟳

TICK — One step forward

A tick is a single unit of progress inside the loop. At each tick, the agent reads the current state of the problem — what has been found, what tools have been run, what evidence exists — and decides what to do next. A tick always ends with a concrete output: a tool was called, a hypothesis was updated, a branch was pruned, or a conclusion was reached. The loop state is saved to the database after every tick so the investigation can resume exactly where it left off if interrupted.

Example: Tick 1 — agent reads the current hypothesis ("JWT may accept alg=none") and the tool output from the previous step (server returned HTTP 200 to an unsigned token). It updates confidence from 0.6 to 0.9 and emits a candidate finding. Tick complete. State saved.
⎇

BRANCH — Every possible next move

At each tick, the agent does not commit immediately. It first generates multiple candidate branches — all the reasonable next steps it could take. Each branch is a different direction the investigation could go. Branches are evaluated and scored. Branches with high potential evidence value are kept. Branches that lead to dead ends, repeat already-tested paths, or fall outside scope are pruned and discarded.

Example branches when testing an upload endpoint:
  • Branch A — test with a file whose content type says image but contains a script (content-type mismatch)
  • Branch B — test with a path traversal in the filename (../../../etc/passwd)
  • Branch C — test with a ZIP bomb to check for resource exhaustion
  • Branch D — test with a double-extension file (shell.php.jpg)
Branches B and D score highest based on prior findings about the server's technology. A and C are queued for later. The agent picks the highest-scoring branch first.
→

CHOSEN PATH — The deliberate next action

The chosen path is the branch the agent commits to for the current tick. The choice is not random — it is based on evidence score, hypothesis confidence, coverage gaps, and judge/supervisor directives. Once chosen, the agent executes the action (calls a tool, updates a hypothesis, emits a finding, escalates to a subagent), records the result, and returns to the top of the loop for the next tick.

Key property: The chosen path and the reason it was chosen are both recorded. This means a human reviewer can read the full investigation trail and understand not just what GENESIS tested, but why it tested that specific thing in that specific order. The investigation is auditable end to end.

How the Loop Knows When to Stop

Every reasoning loop has an exit condition — a specific state that means the current problem is resolved. Common exit conditions are:

  • Proof confirmed: The oracle for the current hypothesis has been satisfied — the vulnerability is real and proven. The loop emits a CANDIDATE_FINDING and exits.
  • All branches exhausted: Every reasonable path has been tested and none confirmed the hypothesis. The loop marks it unverified or ruled out and exits.
  • Escalation needed: The current agent does not have the right tools or scope for the next branch. The loop flags the hypothesis for a specialist agent and suspends.
  • Coverage threshold reached: The loop has explored enough branches to satisfy the coverage gate for the current scan profile. It saves a coverage artifact and exits cleanly.

The Eight Reasoning Loop Types in GENESIS

Different problems require different thinking structures. GENESIS routes each hard problem to the loop type best suited to solve it. An agent triggers a loop using the deliberate(loop_type='...') command.

Loop Type

Tree of Thought

When used: When there are many possible attack approaches and the agent needs to explore several in parallel before committing.
What it does: Grows a tree of branches, scores each, pursues the highest-confidence paths deeper, and prunes the rest. Like a chess player thinking 4 moves ahead on 3 different lines simultaneously.

Loop Type

Hypothesis Decomposition

When used: When a hypothesis is too broad to test in one step ("this login system might be insecure").
What it does: Each tick breaks the hypothesis into one smaller, testable claim. Branches represent different ways to decompose. Chosen path is the sub-claim most likely to confirm or disprove the parent hypothesis fastest.

Loop Type

Counterfactual

When used: When the obvious attack is blocked and the agent needs to think around it.
What it does: Each tick asks "if this assumption were false, what would be true?" Branches represent alternative assumptions. Chosen path is the assumption most likely to open a new attack avenue. This is how GENESIS finds the non-obvious bypass routes.

Loop Type

Causal Trace

When used: When GENESIS sees an unexpected server response and needs to find the root cause in code.
What it does: Each tick steps one level further back in the causal chain. Branches represent different possible causes at each level. Chosen path follows the most specific, evidenced cause. Ensures fixes address root causes, not surface symptoms.

Loop Type

Chain Composer

When used: After multiple individual confirmed findings exist and the agent asks "can these be combined into one bigger attack?"
What it does: Each tick attempts to link one more finding into the growing chain. Branches represent different linkage orders. Chosen path extends the chain with the finding that most increases combined severity.

Loop Type

Invariant Tracker

When used: When source code is available and the agent needs to verify that security rules are enforced everywhere, not just in one place.
What it does: Each tick checks one location where the invariant should hold. Branches represent different code paths. Chosen path is the location most likely to be missing the check based on the code structure.

Loop Type

Long-Context Code Analysis

When used: When source files are very large (100,000+ lines) and the agent needs to reason across the entire file.
What it does: Each tick processes one segment of the file and carries forward a running summary. Branches represent alternative interpretations of the code's security model. Chosen path follows the interpretation with most supporting evidence.

Loop Type

Self-Correcting

When used: After the agent has produced an analysis that may contain errors, contradictions, or unsupported assumptions.
What it does: Each tick critiques one aspect of the previous reasoning. Branches represent possible corrections. Chosen path is the correction that most improves logical consistency. This is the built-in quality control loop.

Reasoning Loops in the Context of the Full Investigation Flow

Reasoning loops do not replace the main investigation flow — they plug into it at the points where a single observation is not enough to reach a conclusion. When the main loop hits a complex sub-problem, it delegates to a reasoning loop. The reasoning loop runs its tick-branch-choose cycle until it has an answer, then returns that answer to the main flow. The main flow continues from there, now with a richer, more evidence-grounded conclusion than a single-step approach would have produced.

Preventing Drift — Staying on Track Over Time

The more ticks a reasoning loop runs, the higher the risk of drift — gradually shifting focus away from the original goal toward interesting but off-target branches. GENESIS prevents this with two mechanisms:

  • Loop State Persistence: After every tick, the full loop state — current branch scores, pruned paths, chosen path history, and running evidence summary — is saved to MongoDB. If a session is paused, interrupted, or the model context is compressed, the loop resumes from the exact tick it was at. No progress is lost and no tick is repeated.
  • Anchor to Original Goal: At the start of each tick, the loop re-reads the session goal and the original hypothesis that triggered it. If the chosen path drifts more than a defined distance from the original goal, the loop flags itself to the Session Supervisor, which can redirect it with a corrective directive.
  • Drift Detection (Weekly Audit): A scheduled background process compares loop state records across all completed sessions to detect systematic patterns of goal abandonment. If a loop type consistently drifts in a particular attack class, the loop's scoring weights are adjusted.

Validation Pipeline — From Suspicion to Confirmed Fact
The process that ensures every reported finding is real, not theoretical.
Analogy — The Evidence Standard in Court

In a criminal case, a suspicion is not enough to convict — evidence must meet a specific standard. GENESIS applies the same principle: an agent's belief that something might be vulnerable is not enough to put it in the final report. The finding must pass through four independent reviewers and then be proven by a live test. Only then is it "convicted" — promoted to a confirmed vulnerability.

Stage 1 — Candidate Extraction

When an agent believes it has found a vulnerability, it emits a CANDIDATE_FINDING block — a structured claim containing: what type of vulnerability it is (attack class), which specific endpoint or code location is affected, what the evidence is, and a proposed way to prove it. This candidate is stored in MongoDB and deduplicated — if two agents independently find the same thing, their evidence is merged into one candidate rather than creating two separate findings.

Stage 2 — Four Independent Validators

Each candidate passes through four automated validators. Each validator gives a verdict: pass, flag, or block. A single block verdict stops the candidate from proceeding.

ValidatorWhat It Checks
Evidence ValidatorIs there actual evidence for this claim, not just speculation? Is a proof plan included?
Endpoint ValidatorFor findings that claim a live endpoint is vulnerable — is the endpoint actually reachable? Is there a concrete testable signal?
Source ValidatorFor findings based on code analysis — is a specific file, function, and dangerous operation identified? Is there taint-flow evidence showing how attacker input reaches the dangerous operation?
Counter ValidatorAre there any contradictions? (e.g., a finding claims a vulnerability requires unauthenticated access but the endpoint is clearly authenticated-only)

Stage 3 — Proof Planning and Execution

Candidates that pass all four validators proceed to proof. A Proof Planner generates a specific, safe, deterministic test — a carefully crafted input or request that will either confirm or deny the vulnerability without causing harm. This test is executed against the live target (or the Forge Sandbox for dangerous payloads).

The result is compared against a pre-defined oracle — an expected outcome that constitutes confirmation. For example: "If we send this SQL injection payload to the search endpoint, the response will contain data from another user's account." If the oracle is satisfied, the proof passes. If not, the finding is returned to candidate status for further investigation.

Patch-Semantic Deduplication

In long investigations, GENESIS may find several findings that look superficially different but would actually be fixed by the same code change. Rather than presenting these as separate items in the report, a final deduplication step asks: "Would fixing finding A also fix finding B?" If yes, they are grouped under a single report entry with a combined severity. This ensures remediation teams are not overwhelmed by redundant tasks.

A Real Finding, Explained End to End
Follow one vulnerability from the moment GENESIS noticed something unusual to the final report entry.

The following walkthrough traces a real confirmed finding — a critical vulnerability where an attacker can access cloud credentials by making the application fetch a URL it should never reach. We follow it through every step of the GENESIS process.

The Finding: SSRF — Server-Side Request Forgery to Cloud Credentials

Plain English Explanation of This Vulnerability

Imagine a corporate receptionist who will fetch any document you ask them to get, including documents from the company's private filing cabinet. SSRF is exactly this: the web application has a feature that fetches URLs. An attacker provides not a public URL, but the address of an internal company resource (in cloud environments, this is a special address that returns cloud access keys). The application dutifully fetches it and returns the secret keys to the attacker. These keys can then be used to access the company's entire cloud environment.

Step 1 — Recon Agent Discovers the Endpoint

The Recon Agent maps all API endpoints. It finds /api/fetch?url= — a feature that takes a URL as a parameter and fetches it. This is published to the shared findings channel immediately.

Step 2 — Analyst Agent Forms a Hypothesis

The Analyst Agent reads the shared finding and knows that any URL-fetching feature is a candidate for SSRF attacks. It emits a hypothesis: "The /api/fetch endpoint may not validate whether the provided URL points to internal or restricted resources. Confidence: 0.65."

Step 3 — Network Agent Tests the Hypothesis

The Network Agent runs a Hypothesis Decomposition loop, breaking the broad hypothesis into specific testable claims: (a) can we reach localhost? (b) can we reach internal Docker network addresses? (c) can we reach the cloud metadata service? It runs the SSRF probe tool against each case.

Step 4 — Initial Probe: Partial Block Discovered

The tool finds that sending ?url=http://127.0.0.1 is blocked. A blocklist exists. The hypothesis confidence drops slightly. The Counterfactual reasoning loop activates: "If direct IP is blocked, what bypasses exist?" It generates 4 alternatives: (a) trailing dot hostname, (b) octal encoding, (c) use a hostname that resolves to 127.0.0.1, (d) use the Docker internal hostname metadata.

Step 5 — Bypass Found

Alternative (d) succeeds. The blocklist only checks for the literal string "127.0.0.1" and a handful of hostname strings, but it does not resolve hostnames to their IP addresses first. Sending ?url=http://metadata/latest/meta-data/iam/security-credentials/demo bypasses the filter because "metadata" is not in the blocklist — even though it resolves to an internal address. The response contains cloud access keys. Hypothesis confidence: 0.97.

Step 6 — Red-Blue Adversarial Debate

Red: "This is a critical SSRF. The blocklist is bypassed by hostname, cloud credentials are returned, and these credentials can be used to access the entire cloud environment." Blue: "The application has a blocklist — it is making an effort to protect itself. Also, the returned credentials may be test credentials with limited scope." Red (counter): "The blocklist specifically fails to resolve hostnames, which is a documented SSRF bypass. The credentials are labeled 'ASIAGENESISDEMO' but the pattern is identical to real AWS credential responses. The same technique works against any hostname-based cloud metadata service." — Red survives. Confidence boosted to 1.0.

Step 7 — Four Validators Pass

Evidence Validator: ✓ (HTTP response containing credentials in evidence). Endpoint Validator: ✓ (endpoint reachable, concrete response). Source Validator: ✓ (function `_blocked_ssrf_target()` identified with specific line-level sink). Counter Validator: ✓ (no contradictions).

Step 8 — Proof Execution

The forge_runner sends the exact bypass URL to the live endpoint. The oracle checks: does the response body contain the string "ASIAGENESISDEMO" AND a field matching AWS credential format? Yes. Proof passes. Finding is promoted to Confirmed Vulnerability.

Step 9 — Chain Assembly

The Chain Composer links this finding to two other confirmed findings in the same session: "unauthenticated admin token endpoint" and "source code disclosure exposing JWT secret." The resulting chain: unauthenticated access → forge admin JWT → use SSRF bypass → steal cloud credentials. This chain is scored at CVSS 10.0 — the maximum possible severity.

Step 10 — Final Report Entry

The finding appears in the report with its severity badge, CVSS score, step-by-step attack demonstration, MITRE ATT&CK technique codes (T1552.005 — Cloud Instance Metadata API; T1190 — Exploit Public-Facing Application), and a specific three-line code fix for the _blocked_ssrf_target() function.

Patches, Exploitation & Recommendations
How GENESIS goes beyond finding problems to telling you exactly how to fix them.

Remediation Generation

For every confirmed finding, GENESIS generates a remediation recommendation at the appropriate technical level. If source code is available, the recommendation names the specific file, function, and line number that needs to change, and often includes the corrected code. If only the running application is available, the recommendation describes the architectural or configuration change needed.

Remediations are written at three levels to serve different audiences:

For Developers

Technical Remediation

Specific code changes: which function to modify, what logic to add, what library to replace. Written with enough precision that a developer can implement the fix without further research.

For Architects

Architectural Remediation

Design-level recommendations: which component boundary should move, what trust model should be enforced, what security control should be added at the infrastructure level.

For Leadership

Risk Summary

Plain-English impact statement: what an attacker can actually do if this is exploited, what data or systems are at risk, and what the business consequence of a successful attack would be.

CVSS Scoring

Every finding is assigned a CVSS score — a standardised industry number between 0 and 10 that measures how severe a vulnerability is. GENESIS calculates this score based on: how easy it is to exploit, whether authentication is required, what access the attacker gains, and what data or systems are affected. A score above 9.0 is Critical — meaning it should be fixed within 24-48 hours of discovery.

MITRE ATT&CK Mapping

MITRE ATT&CK is an internationally recognised framework that catalogues every known attacker technique. GENESIS automatically maps every confirmed finding to its corresponding MITRE technique codes. This enables your security operations team to correlate GENESIS findings with threat intelligence, understand which attack patterns attackers are using in the wild, and ensure your detection systems are monitoring for the right behaviours.

Exploitation Evidence

For critical and high-severity findings, GENESIS captures a complete exploitation record: the exact request sent, the response received, screenshots of the impact, and the proof oracle result. This evidence serves two purposes: it proves to sceptical stakeholders that the vulnerability is real (not theoretical), and it provides developers with the exact reproduction case they need to test that their fix works.

Questions CISOs and Directors Should Ask
Due diligence questions for evaluating GENESIS — with the answers.
Q1: How do we know the findings are real and not false alarms?
Every finding in the GENESIS report has passed through a 4-stage validation pipeline and has been proven by an actual live test against your system. The proof result — including the exact request sent and response received — is attached to each finding. Nothing is reported as confirmed unless it has been demonstrated to work. In the benchmark evaluation against a test application with 8 known planted vulnerabilities, GENESIS achieved 0% false positive rate (0 false alarms) and 100% detection rate (all 8 found).
Q2: Is GENESIS going to break our production systems?
GENESIS is designed to be non-destructive. For potentially dangerous payloads, it tests against an isolated Forge Sandbox replica before touching your live environment. All proof tests sent to live systems are carefully crafted to confirm the vulnerability without exploiting it destructively — for example, using a read-only SQL injection that returns data without modifying it. GENESIS does not run denial-of-service tests, does not delete data, and does not modify application state unless explicitly authorised to do so.
Q3: How is this different from the penetration tests we already do?
Traditional penetration testing involves skilled humans spending typically 1-2 weeks on a target. Their coverage depends heavily on the individual tester's experience, available time, and the scope they were given. GENESIS can run a Deep Research scan of equivalent or greater depth in hours, across the full attack surface, with 15 specialist agents working in parallel, 24/7, as frequently as needed. It also remembers what it found in previous scans of the same target, allowing it to focus new scans on what has changed. Human penetration testers are excellent for creative, context-driven assessments — GENESIS is excellent for broad, systematic, repeatable coverage at scale.
Q4: Who can see the findings? How is the data secured?
GENESIS operates entirely within your controlled environment. All data — findings, session records, proof evidence, credentials used during testing — remains on your infrastructure. There is no call home to external services for result storage. Role-based access controls govern who can view findings in the GENESIS interface. All finding data is persisted to your PostgreSQL and MongoDB instances, which are under your control and your retention policies.
Q5: How does GENESIS prioritise what to fix first?
GENESIS provides two priority dimensions: CVSS severity score (the industry standard measure of how severe a vulnerability is) and attack chain membership (whether the finding is part of a multi-step attack path to a high-value target). A medium-severity finding that is the first step in a chain ending in cloud credential theft will be flagged more prominently than a standalone critical finding with no further exploitation potential. Recommended remediation order follows: P0 (fix immediately — enables full compromise chains), P1 (fix within sprint — significant standalone risk), P2 (fix within quarter — hardening).
Q6: Can GENESIS find vulnerabilities that no one has ever seen before?
Yes — this is one of GENESIS's design goals. The Philosopher Agent specifically looks for novel vulnerability classes not represented in any standard database. In the benchmark evaluation against OWASP Juice Shop v20.0.0, GENESIS identified 50 novel candidates representing 12 distinct vulnerability classes not in any official challenge database, including a hash length-extension attack that required reasoning about multiple cryptographic conditions simultaneously. These are flagged as "novel candidates" in the report and carry a note that they represent potential zero-day risk.
Q7: How often should we run GENESIS scans?
GENESIS supports continuous scanning models. A baseline deep scan should be run at the start of major development cycles or before significant releases. Lighter-weight scans should be run on any meaningful code change. The Surface Watcher background process monitors your attack surface hourly and can trigger targeted scans when new endpoints or services appear. For applications handling sensitive data or operating in regulated industries, monthly deep scans plus continuous surface monitoring is the recommended baseline.
Q8: What is the risk if GENESIS itself is compromised? Does it have privileged access?
GENESIS is designed with a minimal-privilege model. Scanning credentials (API tokens, test accounts) used during a session are scoped to the session and rotated regularly. The platform itself should be operated in an isolated scanning network segment with no broader access to production infrastructure. All internal communications use authentication tokens. The production hardening plan includes replacing all default credentials with cryptographically random values, enforcing non-root container execution, and adding TLS to all internal service connections.
Q9: Can we see what GENESIS is thinking as it investigates?
Yes. GENESIS provides a real-time web interface showing: every agent's current reasoning (agent thoughts), every tool being called and its result, the current hypothesis market with confidence scores, the emerging attack graph, and the Red-Blue debate transcripts. Leaders who want to observe the investigation in progress can watch a live feed of the entire process. Every decision GENESIS makes is logged and auditable after the fact.
Q10: What happens if GENESIS finds something that our team disagrees with?
Every finding includes its full evidence chain: the original hypothesis, the tool outputs that informed it, the adversarial debate transcript, and the proof result. If your team believes a finding is incorrect, they can review this complete evidence trail. Findings can be marked as "disputed" in the system, which flags them for human expert review without removing them from the record. Disputed findings are tracked separately and contribute to GENESIS's calibration — if a pattern of disputes reveals a systematic error, the detection logic is updated.

Immediate Priority — Platform Hardening (Before Production Deployment)

Replace Default Credentials

All default passwords (including the database password visible in configuration) must be replaced with cryptographically random values. Current state is acceptable for lab environments only.

P0 — Do Before Go-Live

P0 — Do Before Go-Live

The GENESIS platform's own authentication endpoints need rate limiting to prevent brute-force attacks against the platform itself.

Coverage Gaps Identified in Benchmark Analysis

P1 — High Impact Gap

Web3 / Blockchain Vulnerability Coverage

OWASP Juice Shop v20 introduced smart contract vulnerabilities (NFT Takeover, Wallet Depletion, Mint Honey Pot). The v20 benchmark showed these were not covered. A Web3 specialist agent with tools for Solidity analysis, smart contract fuzzing, and blockchain state manipulation is needed for organisations operating blockchain-based systems.

P1 — High Impact Gap

AI/LLM Security Testing

As organisations deploy AI chatbots and LLM-powered features, a new attack class has emerged: prompt injection, context window manipulation, training data extraction, and model denial-of-service. The v20 benchmark identified 3 Chatbot/AI challenges. A dedicated LLM security specialist agent should be added to GENESIS's specialist roster.

P1 — High Impact Gap

OSINT and Social Engineering Surface

GENESIS currently has strong technical coverage but limited open-source intelligence (OSINT) capability — finding leaked credentials in public repositories, exposed internal documents, or employee information that enables targeted attacks. An OSINT specialist agent would significantly expand coverage of the initial access phase.

P1 — High Impact Gap

Browser-Side JavaScript Analysis

Several challenge categories in the benchmark involved client-side JavaScript vulnerabilities (DOM-based XSS, browser-side logic flaws, postMessage abuse). GENESIS has browser tools but dedicated client-side code analysis — reading and understanding JavaScript running in the browser — would improve coverage of this class.

Enhancement Opportunities

P2 — Medium Impact

API Discovery Coverage

GraphQL endpoints, hidden API versions, shadow APIs (undocumented endpoints left in production), and developer tooling left exposed in production remain under-covered. Enhanced API enumeration during the recon phase would improve coverage of modern application architectures.

P2 — Medium Impact

Authenticated Scan Depth

Many of the most impactful vulnerabilities — business logic flaws, privilege escalation, IDOR — require authenticated access to test effectively. Expanding GENESIS's ability to maintain complex authentication state across multiple user roles would unlock deeper coverage of authenticated attack scenarios.

P2 — Medium Impact

Supply Chain Dependency Analysis

The benchmark showed that direct mapping of third-party component vulnerabilities (known-vulnerable libraries) was at 28.9% (v14.5.1) and 20.7% (v20). Integrating a dedicated software composition analysis (SCA) engine with a richer dependency graph would improve identification of vulnerable components in application dependencies.

P2 — Medium Impact

Multi-Application Correlation

When GENESIS has scanned multiple applications in an organisation's portfolio, it has the data to identify cross-application patterns: credentials from Application A that work on Application B, vulnerabilities in shared libraries affecting multiple apps, trust relationships between applications that create multi-hop attack paths. Cross-session correlation analysis would surface these organisation-wide risks.

P3 — Longer Term

Continuous Monitoring Mode

Moving from periodic scan sessions to a continuous monitoring model where GENESIS watches for changes to the attack surface and automatically triggers targeted scans when meaningful changes are detected. The Surface Watcher process is the foundation — this extends it to a full continuous security posture management capability.

P3 — Longer Term

Developer IDE Integration

Bringing GENESIS's code analysis capabilities directly into developer environments (VS Code, IntelliJ) so that security feedback is available during development rather than post-deployment. This shifts security left in the development lifecycle — the most cost-effective point to fix vulnerabilities.
