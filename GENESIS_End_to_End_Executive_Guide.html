Plain English Summary

What GENESIS is

GENESIS is an AI-driven security research platform. It does not just run a list of scanners. It observes a target, forms hypotheses, chooses tools to test those hypotheses, learns from results, validates evidence, and produces findings with proof, remediation, and executive reporting.

What starts a scan

A user creates a research session with a target, scan profile, and agent mode. The backend stores the session, then a Celery worker runs the long investigation in the background so the UI remains responsive.

What makes it different

GENESIS keeps an investigation journal. It saves goals, thoughts, hypotheses, evidence, tool outputs, validation verdicts, and attack graph knowledge. This lets it revisit unresolved leads instead of forgetting them as the model context changes.

What a final finding needs

A final finding needs concrete evidence. In strict validation mode, a candidate must pass proof steps before it becomes a confirmed vulnerability. If evidence is weak, the finding stays disputed, unverified, or ruled out.

Simple Analogy: A Security Investigation Team

A normal scanner is like a guard with a checklist: check every door, window, and lock, then report which ones looked weak.

GENESIS is more like a senior investigation team inside a command room. One person maps the building. Another studies the access badges. Another reviews old incidents. Another challenges the evidence. Another tests the risky theory in a safe replica room. A lead investigator keeps the goal on the wall so the team does not drift.

Simple example: A scanner might say, "Endpoint /api/users/123 returned data." GENESIS asks, "Can one user change the number and read another user's data? Is there an ownership check? Can I prove it with two roles? If true, what is the impact and what exact fix should engineering make?"

End-to-End Flow

The flow below shows the complete lifecycle from initiation to final report.

Session is created

The frontend calls the backend to create a research session. The request contains the target, scan profile, agent mode, and optional configuration. The backend validates the target, stores the session in PostgreSQL, and sets the initial phase to reconnaissance.

Session is started

The backend changes the session from pending to running, records the start time, publishes a live update, and sends a background task to Celery on the research queue.

Celery worker launches the orchestrator

A worker receives the task, resets asynchronous service clients for its worker process, creates the AI orchestrator, and runs the session. If the task fails, the worker stores the error, marks the session failed, and cleans containers related to the session.

Settings, memory, and prior knowledge are loaded

GENESIS loads live application settings, model routing rules, MCP connection settings, prior findings for the same target, vector memory from ChromaDB, graph knowledge from Neo4j, and historical session data from MongoDB and PostgreSQL.

Goal and target brief are created

If the user did not provide a detailed goal, GENESIS compiles a default goal. It also creates a target intent brief: what the target seems to be, likely assets, likely risk areas, and how to prioritize the investigation.

Plan tree is seeded

The system creates a plan tree. This is a living roadmap of work to do, work completed, open branches, attack classes, and unresolved leads. It is saved outside the model context so the investigation can continue over many iterations.

Reconnaissance begins

GENESIS discovers services, endpoints, technologies, ports, domains, screens, APIs, artifacts, source code clues, and prior intelligence. It does not treat recon as a one-time step. New recon can happen later whenever a new lead appears.

Hypotheses are formed

GENESIS writes structured hypotheses such as: "This endpoint may allow IDOR because user IDs are sequential and ownership was not checked." Each hypothesis includes confidence, supporting evidence, opposing evidence, the next test, and what would falsify it.

Tools are called to test hypotheses

The orchestrator selects tools based on what it is trying to prove or disprove. It may call standard scanners, custom probes, browser automation, request forgers, binary analysis, fuzzers, symbolic execution, code readers, graph search, or sandboxed exploit runners.

Results are saved and interpreted

Tool outputs are saved to MongoDB. The model reads the output, updates hypotheses, adjusts the plan, and may create candidates. Screenshots, DOM output, console logs, network logs, proof markers, and artifacts are preserved when available.

Agents and subagents collaborate

In multi-agent mode, recon, analyst, exploit, code, payload, and specialist agents work in phases. They share findings through Redis so one agent can build on another agent's discovery instead of repeating it.

Critic and adversarial agents challenge evidence

The critic reviews evidence before a finding is trusted. Red and blue agents debate hypotheses. The philosopher agent looks for deeper explanations behind anomalies. Insider and nation-state agents look for abuse paths a normal scanner might miss.

Validation pipeline proves or rejects candidates

Candidate findings go through validators, proof planning, deterministic proof runs, verdicts, clustering, and promotion. A candidate becomes a real vulnerability only after it passes the required evidence gates.

Final findings are saved, mapped, and reported

Confirmed vulnerabilities are saved in PostgreSQL, linked in Neo4j, embedded into ChromaDB for future recall, enriched in MongoDB, mapped to MITRE or CVE/CWE-style signatures where available, and included in HTML, Markdown, API, and CSV reporting.

Knowledge is retained for the future

The system updates high-water marks, attack graph knowledge, vulnerability embeddings, specialist memory, goal progress, and reproducibility reports. This gives later sessions a better starting point.

Scan Initiation

A scan begins as a research session. The user supplies a target and chooses how deep the investigation should be.

What the user provides

  • Target IP, hostname, application, or approved scope.
  • Scan profile, such as quick, deep research, exhaustive, web, or SSL-oriented.
  • Agent mode, usually solo or multi-agent.
  • Optional config such as operator notes, credentials, policy, or validation preferences.

What the backend does immediately

  • Validates that the target is not an obviously unsafe internal special address such as loopback or multicast.
  • Creates a PostgreSQL session record with status pending and phase reconnaissance.
  • When started, changes status to running and sends a Celery task to the research queue.
  • Publishes a live status update so the frontend can show progress.
Executive translation: A GENESIS scan is not a single API call that returns a static result. It is a managed investigation with status, scope, timeline, evidence, validation, and reporting.

Goals and Iteration Planning

GENESIS keeps a goal in front of the investigation so it does not wander. The goal can be user-provided or automatically compiled from the target and scan profile.

Planning item How GENESIS uses it Where it is saved
Goal tree Breaks the broad mission into concrete objectives, such as map exposed services, test authentication, evaluate injection risk, validate findings, and produce a report. MongoDB and PostgreSQL goal records
Target intent brief Summarizes what the target appears to be, likely business purpose, likely sensitive assets, and high-value areas. MongoDB target_briefs
Plan tree Tracks what has been explored, what remains, and what branches need follow-up. MongoDB plan_trees
Iteration counter Records progress across the long-running loop. The counter is monotonic and stored outside the model context. PostgreSQL research_sessions
Coverage gates Prevent early stopping until enough attack classes, endpoints, duration, or goal progress have been covered for the scan profile. Orchestrator runtime state, MongoDB coverage artifacts, PostgreSQL session status

How iterations are planned

  1. GENESIS starts with reconnaissance and prior memory.
  2. It creates or updates hypotheses based on observations.
  3. It picks the next best test for the highest-value hypothesis.
  4. It calls tools through MCP or internal reasoning loops.
  5. It stores outputs, updates confidence, and either confirms, disputes, or continues testing.
  6. It periodically asks an independent judge to identify gaps.
  7. It stops only after the scan profile's minimum work, coverage gates, and goal conditions are satisfied.

Recon and Hypothesis Formation

Reconnaissance is how GENESIS learns what the target is. Hypothesis formation is how GENESIS turns observations into testable security questions.

Recon examples

  • Find open ports and services.
  • Identify web technologies, frameworks, headers, and TLS settings.
  • Discover endpoints, directories, parameters, GraphQL, forms, APIs, and login flows.
  • Pull artifacts such as scripts, binaries, package files, source snippets, or firmware-like assets.
  • Use browser rendering to see what a real user would see.
  • Recall previous findings and patterns for the same or similar targets.

Hypothesis examples

  • "The user object endpoint may lack object-level authorization."
  • "The upload flow may allow parser confusion because file type checks differ between client and server."
  • "The JWT flow may accept a weak or confused signing algorithm."
  • "The binary may contain a reachable memory corruption path near input parser X."
  • "The API may have a race condition because balance updates are split across two requests."

What a hypothesis contains

GENESIS records hypotheses in a structured way. Each one normally includes an ID, statement, confidence, evidence for, evidence against, next test, falsification criteria, attack chain ID, and status. 

{
  "id": "h-id-001",
  "statement": "The /api/users/{id} endpoint may expose other users' data.",
  "confidence": 0.62,
  "evidence_for": ["Sequential user IDs", "Endpoint returns full profile"],
  "evidence_against": ["Only one role has been tested so far"],
  "next_test": "Use two valid accounts and request another user's ID",
  "falsification_criteria": "A non-owner request returns 403 or only self-scoped data",
  "status": "testing"
}
Key idea: The hypothesis is not the finding. It is a testable theory. It becomes a candidate or finding only when evidence supports it strongly enough.

Tool Selection and MCP Integration

GENESIS selects tools based on the current question. If the question is "what is exposed?", it uses recon tools. If the question is "can this be exploited?", it uses proof tools. If the question is "what does this binary do?", it uses decompilation, fuzzing, symbolic execution, or instrumentation.

How tools are called

  1. The AI orchestrator decides a tool is needed and builds parameters.
  2. The backend MCP client maps the AI-facing tool name to an MCP server tool name.
  3. The MCP server validates the request and executes either a local binary tool or an HTTP-backed helper service.
  4. The MCP server returns structured output to the backend.
  5. The backend saves the output, publishes a live event, and gives the result back to the reasoning loop.

Backend MCP client Posts tool requests to the MCP server endpoint. It can include an API key and maps friendly tool names to actual MCP tool names. nmap_scan becomes nmap; sqlmap_test becomes sqlmap.
MCP REST server Exposes health, tool listing, tool metadata, test endpoints, and /tools/execute. The backend calls one consistent interface instead of shelling out directly.

Agents, Subagents, Critic, Compression, and Adversarial Reasoning

GENESIS can run in a single-agent loop or a multi-agent workflow. In both cases, it uses specialist roles when they add value.

Agent or role When it is called What it contributes
Primary orchestrator Runs throughout the session. Owns the main loop, goals, hypotheses, tool calls, evidence, validation handoff, and finalization.
Recon subagent Early in multi-agent mode, before deep exploit work. Maps services, endpoints, technologies, and exposed areas.
Analyst subagent Early in multi-agent mode and during later rounds if needed. Turns observations into theories, correlations, and likely attack paths.
Exploit subagent After recon/analysis or when there is a candidate proof path. Attempts authorized proof using safe tools such as request forge, payload swarm, browser session, or sandbox runner.
Code subagent When source code, packages, artifacts, or code-like assets are available. Looks for taint, invariants, risky code patterns, reachable sinks, and patchable root causes.
Payload subagent Phase 2 in multi-agent mode. Generates payload candidates. It does not own final proof; exploit agents consume the candidates and test them.
Specialist agents When surfaces or memory indicate a specific domain. Crypto, authentication, network, reverse engineering, exploit development, source analysis, IoT, mobile, OT, and embedded review.
Critic When a finding is confirmed/exploited, or when an unverified claim has medium or high confidence. Challenges the evidence and can mark a claim confirmed, disputed, or unverified.
Red/Blue dialectic Seeded after early discovery and after important confirmed hypotheses. Red proposes attack hypotheses; Blue challenges feasibility and evidence. Surviving ideas go back into the hypothesis market.
Philosopher agent Later in the scan, after enough anomalies exist. Reasons from first principles about what underlying bug class might explain observed oddities.
Insider threat agent Later in deep or multi-agent work. Looks for misuse paths by someone with partial access, weak internal controls, or privileged workflow knowledge.
Nation-state agent Later in deep or multi-agent work. Considers stealthier, chained, patient attack paths that may not look obvious in a normal scan.
Session judge Periodically, such as every 25 solo iterations or after multi-agent rounds. Scores coverage, identifies gaps, and says whether the session is mature enough to stop.
Session supervisor After judge verdicts identify gaps. Turns gaps into directives for the right agent type through Redis queues.
History compressor Periodically during long sessions. Compresses older conversation history while preserving key progress, findings, and next steps.
Persona orchestrator When persona mode is enabled. Runs optional perspectives such as paranoid pentester, ransomware operator, nation-state APT, insider threat, and opportunistic attacker.

How subagents coordinate

Subagents do not work in isolation. They publish shared findings to Redis. Other agents read those findings so they can avoid repeating work and can build on a teammate's discovery. The system caps shared findings and expires them after a time window so the session stays fresh.

When compression happens

Long AI sessions can exceed the model's context window. GENESIS periodically compresses older history into a compact progress summary while keeping recent messages and critical instructions. This is paired with saved plan trees, hypotheses, and tool outputs so the model can remember the mission without carrying every old token.

Celery Worker Task Handling

Celery is the background job system. It lets GENESIS run long investigations and validation proof jobs without blocking the API server.

Task dispatch

The backend sends run_research_session(session_id, target_ip) to the research queue when a user starts a session.

Worker preparation

The worker resets async service clients such as Redis, MongoDB, ChromaDB, Neo4j, and artifact resolution because prefork worker processes use separate event loops.

Orchestrator execution

The worker creates the AI orchestrator and runs the session loop until completion, pause, stop, failure, or timeout.

Heartbeat

Workers can publish capability heartbeats to Redis so the platform knows which worker capabilities are alive.

Failure handling

If the task fails, the worker stores the error in MongoDB, updates PostgreSQL session status to failed, and cleans any session containers.

Validation completion

Separate Celery jobs can run validation proof completion. These jobs process candidates, execute proof tools, store proof runs, and promote findings when ready.

Reasoning Loops and Drift Control

GENESIS does not rely on one long free-form chat. It uses bounded reasoning loops and persistent state to keep the investigation grounded.

How GENESIS avoids drifting over time

  • Session state is saved: status, phase, iteration, findings, and counts live in PostgreSQL.
  • Investigation memory is saved: thoughts, tool outputs, hypotheses, plan trees, target briefs, proof runs, and validation verdicts live in MongoDB.
  • Live coordination is external: Redis holds shared findings, directives, live events, Celery queues, and worker heartbeats.
  • Relationships are saved: Neo4j stores services, findings, targets, credentials, and chains.
  • Similarity memory is saved: ChromaDB stores embeddings so similar prior findings can be recalled.
  • Artifacts are preserved: files, screenshots, binaries, and proof outputs are saved in artifact storage.
  • History is compressed: old conversation is summarized, while important state is reloaded from databases.
  • Judges and supervisors check coverage: they identify gaps and assign follow-up work.

Validation Pipeline

Validation is the difference between "the AI thinks this might be true" and "the platform has enough evidence to report it." GENESIS separates candidate findings from confirmed vulnerabilities.

Validation states

candidate proof_queued proof_running proven proof_failed promoted ruled_out source_verified_needs_replay source_verified_unreachable

Pipeline steps

  1. Candidate creation: GENESIS extracts a CANDIDATE_FINDING or SOURCE_CANDIDATE_FINDING from model output, or converts a vulnerability block into a candidate when strict validation is enabled.
  2. Normalization: The system standardizes severity, endpoint, source context, evidence, proof plan, patch key, root cause key, priority, and confidence.
  3. Deduplication: Similar candidates are grouped by deduplication keys so the same root cause does not become many duplicate tickets.
  4. Initial validators: Heuristic, endpoint, source, and counter validators each provide support, refute, or needs-proof signals.
  5. Proof planning: A proof plan is created or refined. It may call live proof tools, static proof tools, source proof tools, or safe replay tools.
  6. Proof execution: Celery can run a validation completion job. Tools are executed through MCP. Results are stored as proof runs.
  7. Verdict update: Passing proof supports the candidate. Failed proof weakens it. Contradictory evidence can dispute or rule it out.
  8. Source replay rule: Source-only candidates need live replay when appropriate. Static evidence alone may be marked source_verified_needs_replay instead of confirmed.
  9. Clustering and surface graph update: The validation layer updates finding clusters and target surface graphs.
  10. Promotion: Only candidates with the required proof are promoted to final PostgreSQL vulnerabilities.

Confirmed, disputed, unverified, and ruled out

Status What it means Typical reason
Confirmed The evidence is concrete enough and validation/critic checks accept it. Proof run passes, evidence is specific, and response behavior matches the hypothesis.
Disputed The idea may be plausible, but evidence is weak, contradictory, or challenged by the critic. Tool output does not prove impact, or a normal behavior explains the observation.
Unverified The lead is not dismissed, but GENESIS has not proven it yet. Needs credentials, needs replay, needs OOB callback, or proof was not completed.
Ruled out Validation found evidence against the candidate. A test returns 403, sanitization works, exploit conditions are not reachable, or the suspected sink is not used.

Exploitation, Patches, Recommendations, and CSV Mapping

GENESIS treats exploitation as authorized proof, not uncontrolled attack behavior. The goal is to prove impact safely and produce remediation that engineering can use.

How exploitation is done

  • Deterministic request forge with pass/fail oracle.
  • Payload swarm to try controlled variants.
  • Browser session for multi-step user flows.
  • OOB checks for blind callbacks.
  • Sandbox or replica execution for risky proof.
  • Fuzzing, symbolic execution, and instrumentation for binary or parser paths.

How patches are formed

  • The finding stores remediation and optional patch code.
  • Source candidates include source context, taint, reachable sink, and root cause key.
  • Patch deduplication groups multiple symptoms of the same root cause.
  • Reports explain the fix in plain language and can include technical patch guidance.

How recommendations are formed

  • Severity and business impact are translated into executive language.
  • Evidence is summarized without requiring raw tool literacy.
  • Remediation is prioritized by impact, exploitability, and affected surface.
  • Recurring root causes are grouped so teams can fix classes, not only symptoms.

CSV mapping

  • CSV exports include finding, severity, target, remediation, tools used, CVSS, signature, and novel.
  • Signature priority is CVE first, then MITRE technique, then technique tag.
  • A finding is marked novel when it is zero-day-like or confirmed through custom proof tooling such as forge_runner, payload_swarm, or AI request forge.

How finding descriptions are produced

GENESIS turns raw security evidence into human-readable language before it reaches the report. A finding description normally explains what was found, where it was found, why it matters, what proof supports it, what the business impact is, and what the recommended fix is. The system keeps the technical evidence available for engineers, but the executive view is written so a non-specialist can understand the risk without reading raw scanner output.

Report outputs

  • HTML report: Executive summary, risk dashboard, areas probed, confirmed vulnerabilities, disputed/unverified items, recommendations, methodology, and technical appendix.
  • Markdown report: Session metadata, executive summary, findings, evidence, attack chains, confirmed hypotheses, and tool histogram.
  • CSV export: Portfolio-friendly list for governance, risk, compliance, and remediation tracking.
  • Identification endpoint: Explains how a vulnerability was identified, which hypothesis drove it, which tool calls supported it, and whether it looks known or novel.
  • MITRE mapping: Aggregates techniques where applicable for security program alignment.

Example Finding: Broken Object-Level Authorization

This example shows how one finding can move through GENESIS. The vulnerability class is often called IDOR or BOLA: a user can access another user's object by changing an ID.

1. Recon observation

GENESIS sees that /api/users/101 returns a user profile after login. User IDs appear numeric and predictable.

2. Hypothesis

GENESIS writes: "The endpoint may lack object-level authorization because the user ID is path-controlled and the response includes sensitive profile fields."

3. Test plan

It plans to use two valid user accounts. User A will request User B's ID. A secure system should return 403 or only self-scoped data.

4. Tool call

GENESIS uses a request forge or IDOR probe through MCP. It sends the same request with User A's token and User B's object ID.

5. Evidence

The response returns status 200 and includes User B's email and account details. The output is saved as tool evidence.

6. Critic review

The critic asks whether the evidence really proves cross-user access. If the tokens and object IDs are clear, the critic supports confirmation. If not, it marks the issue unverified or disputed.

7. Validation

A proof run repeats the request with deterministic pass/fail rules: pass if User A receives User B data, fail if the server blocks it. Passing proof promotes the candidate.

8. Final finding

GENESIS saves a vulnerability with severity, affected endpoint, evidence, impact, remediation, optional patch guidance, and report mapping.

How this is explained to a non-technical leader

Imagine a hospital filing cabinet where every patient's folder has a number. Alice is allowed to open folder 101 because it is hers. If Alice changes the number on the request to 102 and the cabinet gives her Bob's folder, the lock is checking that Alice has a badge but not checking which folder Alice is allowed to open. That is the bug.

Example remediation

requested_user_id = request.path.user_id
current_user_id = auth.current_user.id

if requested_user_id != current_user_id and not auth.current_user.is_admin:
    return error(403, "Forbidden")

return get_user_profile(requested_user_id)

The exact patch depends on the application framework, but the principle is simple: check ownership on the server for every object access. Do not trust the client to only ask for objects it owns.

Why GENESIS Is Not a Basic Automated Penetration Testing Tool

GENESIS can run many tools, but tool execution is not the main idea. The main idea is reasoning through loops and iterations.

Basic scanner or AI endpoint GENESIS
Runs a predefined checklist. Builds a plan, updates it, and changes direction based on evidence.
Finds known signatures well. Can investigate unknown, chained, business-logic, source-driven, and behavior-driven issues.

Methodology Used by GENESIS

GENESIS follows an iterative research methodology. It is close to how an experienced security research team works, but with persistent memory, automation, and repeatable validation.

  1. Define scope and goal: Understand what target is in scope and what the investigation must accomplish.
  2. Build target understanding: Discover exposed services, technologies, endpoints, data flows, roles, and artifacts.
  3. Form hypotheses: Convert observations into testable claims.
  4. Select tools deliberately: Pick the tool that best proves or disproves the current claim.
  5. Run safe proof: Use controlled tool execution, sandboxing, browser automation, or replica testing when appropriate.
  6. Record evidence: Save outputs, screenshots, traces, proof markers, and reasoning state.
  7. Challenge conclusions: Use critic, validators, adversarial debate, and counter-evidence.
  8. Promote only proven findings: Keep unproven leads separate from confirmed vulnerabilities.
  9. Map and explain: Translate findings to severity, business impact, remediation, MITRE/CVE-style mapping where applicable, and CSV/report outputs.
  10. Learn for next time: Save graph relationships, embeddings, high-water marks, and specialist memory.

Questions CISOs and Directors Can Ask About GENESIS

The following questions help leaders evaluate safety, value, coverage, reliability, and operational readiness.

Governance and scope

  • How does GENESIS enforce approved scope?
  • What prevents scans against restricted addresses or assets?
  • Can we define safe, intrusive, and prohibited test categories?
  • Can destructive tests require human approval?
  • How are credentials stored, used, and audited?

Evidence quality

  • What evidence proves each finding?
  • Which findings are confirmed, disputed, unverified, or ruled out?
  • Can we replay the proof?
  • Which tool calls supported the conclusion?
  • What would falsify the finding?

Risk and business impact

  • Which findings expose regulated data or critical business workflows?
  • Which findings are chainable?
  • What is exploitable today versus theoretical?
  • Which fixes reduce the most risk fastest?
  • What findings are novel rather than known scanner hits?

Coverage

  • Which endpoints, roles, services, and attack classes were covered?
  • What areas were not tested and why?
  • Did GENESIS test authenticated and unauthenticated paths?
  • Were business logic and role matrix cases tested?
  • Did the session judge identify remaining gaps?

Operations

  • How long do deep and exhaustive scans run?
  • What are the compute, model, and tool costs?
  • How are worker failures handled?
  • How do we pause, stop, or resume sessions?
  • What evidence is retained and for how long?

Assurance

  • How do critic and validators reduce false positives?
  • How do we benchmark recall and precision?
  • What are the known blind spots?
  • How is model drift detected?
  • How are findings mapped into our ticketing and risk workflow?

Next Steps and Improvement Areas

GENESIS already covers a broad set of web, source, binary, browser, crypto, graph, and validation workflows. The next improvements should focus on uncovered regions, stronger proof automation, enterprise governance, and richer coverage measurement.

Area Current gap or risk Recommended improvement
Authenticated role coverage Business-logic findings often need multiple real roles and realistic test accounts. Add a role matrix input, credential vault integration, and required coverage checks per role.
Cloud and IAM Cloud posture, IAM privilege paths, Kubernetes, serverless, and SaaS integrations need deeper native coverage. Add cloud connectors, IAM graph ingestion, Kubernetes probes, and cloud-specific validation playbooks.
Mobile, IoT, OT, and embedded Specialist agents exist conceptually, but deeper device workflows require more adapters and test harnesses. Add APK/IPA pipelines, firmware unpacking depth, hardware-in-loop notes, protocol simulators, and OT-safe proof modes.
Native exploit proof Some native proof flows reference stronger replica or ASan-style execution capabilities that should be completed and standardized. Finish native replica/proof endpoints, add crash triage, sanitizer evidence, and reproducible exploit harness output.
Human approval gates Deep proof tools can be powerful and should match enterprise risk appetite. Add policy-driven approval checkpoints for intrusive, destructive, credentialed, or OOB tests.
Coverage transparency Executives need to know what was not tested, not only what was found. Add stronger "tested/not tested" matrices for endpoints, roles, attack categories, and source areas.
Validation precision Proof planning can be hard when evidence is partial or source-only. Expand deterministic proof adapters and make validators produce clearer blockers and next proof steps.
Ticketing and ownership Reports are useful, but remediation programs need ownership and SLA routing. Integrate Jira/ServiceNow/GitHub Issues, code owner mapping, SLA labels, and risk acceptance workflow.
Benchmarking Leaders need confidence in precision, recall, novelty, and false-positive rate. Build more ground-truth benchmark ranges, regression suites, and dashboards by category.
Compliance mapping CSV currently focuses on finding, severity, target, remediation, tools, CVSS, signature, and novelty. Add optional CWE, OWASP, NIST, ISO, PCI, HIPAA, and internal control mappings where useful.
Data retention and privacy Evidence can include sensitive response bodies, screenshots, or source data. Add redaction policies, retention classes, encryption review, and export controls per tenant.
Executive readiness Different leaders need different summaries. Add board summary, engineering fix pack, audit evidence pack, and risk acceptance pack templates.
Priority recommendation: The highest-value next step is to strengthen coverage and proof transparency: show what was tested, what was not tested, why proof passed or failed, and what is needed to close each remaining gap.

Glossary

Term Meaning
Hypothesis A testable security theory. It is not a confirmed finding by itself.
Candidate finding A possible vulnerability that has enough structure to enter validation.
Confirmed vulnerability A finding with sufficient evidence and validation to be reported as real.
Critic An AI review role that challenges evidence and reduces false positives.
Red/Blue Adversarial debate where one side proposes attacks and the other challenges them.
MCP The tool execution layer that lets GENESIS call scanners, probes, and helper services through a controlled interface.
Proof run A repeatable test that attempts to prove or disprove a candidate finding.
Attack graph A relationship map showing how targets, services, findings, credentials, and chains connect.
Drift When a long AI session forgets its original goal or loses track of prior evidence. GENESIS reduces drift by saving state outside the model.
