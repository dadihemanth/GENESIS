What GENESIS is

GENESIS is a program you point at a target — a web application, an IP address, a hostname you own — and it tries to find security weaknesses in it. It runs on its own. You don't have to guide it through each step.

Underneath, there is an AI model (Anthropic's Claude) that acts as the "brain." Around it are dozens of standard security tools (Nmap, Nuclei, SQLMap, and so on) plus custom pieces this platform adds — a binary decompiler, a browser, a sandboxed script runner, a pattern library from past sessions, a Neo4j attack graph, a 4-replica payload sandbox, specialist sub-agents, the v4.0 novel-vulnerability research arsenal (differential testing, coverage feedback, 51 new probes — now shipping), and (planned in v5-v8) deeper source-aware reasoning, adversarial hypothesis synthesis, and reasoning loops that compress search space so a generic LLM can match much larger systems within each domain.

Analogy

Think of GENESIS as a junior security researcher you can hire for a few hours. You give them an address to assess. They open a laptop, take notes, run some standard tools, read the output, form guesses about where the weak spots might be, test those guesses, and write up what they find. GENESIS does that — except the "laptop" is a fleet of containers, the researcher never gets tired, and they remember everything they ever learned about every target you've ever scanned.

Who it's for

GENESIS is meant for people who are allowed to test the target. Internal security teams, penetration testers under contract, red-team exercises, bug-bounty researchers on scope, students on a training range. It is not for scanning systems you do not own or do not have written permission to test.

Important

Running an automated security scanner against a target you have no authorization for is illegal in most places. GENESIS does not check authorization — that's on you. See Rules of engagement.

How to use it

You open the web interface (by default at http://localhost:3000). You configure your Anthropic API key once on the Settings page; you start a new session from the dashboard against a target IP or URL with permission to test; you watch the AI work on the session viewer; you read the report when it's done. Confirmed vulnerabilities arrive with severity, evidence, suggested fix, and a full audit trail you can verify yourself.

Reading the results

Every finding GENESIS emits carries a verification status — unverified, confirmed, exploited, or disputed — plus a confidence score. The status is not just "the AI said so." The platform has rules that downgrade a finding when the evidence is weak.

  • Unverified — the AI suggested this may be a problem but couldn't prove it this session. Worth a human look.
  • Confirmed — the AI produced concrete evidence (quoted tool output, a successful exploit round-trip, a callback hit, a passing test predicate).
  • Exploited — the AI actually demonstrated the bug working against the target.
  • Disputed — a second AI reviewed the evidence and decided it doesn't hold up. Treat as false positive.

The autonomous loop (how it runs)

Inside GENESIS there's a loop that repeats up to a certain number of times. Each round is called an iteration. Per iteration: the AI gets the current state, takes an extended-thinking pass, decides whether to run a tool / write a hypothesis / make a report, runs the tool, reads the result, records hypotheses and vulnerabilities in structured form, and moves on. The loop stops when the AI emits FINAL_REPORT, when the loop-breaker forces a wrap-up, or when the session is manually stopped.

Hypothesis-driven testing

Most scanners run checks and tell you what failed. GENESIS is different: it is required to write down what it thinks is happening before it tests it. Every claim is tied back to a hypothesis with: a statement, evidence for and against, the next test, and a falsification criterion — the specific observation that would make the hypothesis wrong. The exact JSON contract used by the orchestrator is documented in Hypothesis JSON contract.

End-to-end data flow

A scan against a single target traces this exact path. Numbered for reference; each step has matching code in the entry-point modules above.

  1. Session creation. Operator submits a target via the Setup Wizard or the Dashboard. Frontend POSTs to /api/v1/sessions. Backend writes a ResearchSession row in PostgreSQL and returns session_id.
  2. Orchestrator startup. Backend kicks off backend/app/services/ai_orchestrator.py for that session. System prompt: "GENESIS MYTHOS" — autonomous red-team operator with hypothesis- driven reasoning, oracle requirements, evidence rules, scan-profile constraints.
  3. 5-phase Claude loop. Each iteration moves through reconnaissance → service_analysis → vulnerability_scan → exploitation → reporting. Claude's tool-use loop fires the Anthropic Messages API with the full tool catalog; the response either contains a tool call (executed below) or a {"HYPOTHESIS": …} / {"VULNERABILITY": …} block.
  4. Tool execution via MCP. Orchestrator calls MCPClient.execute_tool(tool_name, params). mcp_client.py maps Claude tool names (e.g. nmap_scan) to MCP-canonical names (nmap) and HTTP-POSTs /tools/execute. The MCP executor spawns a subprocess (or hits an in-process probe), captures stdout/stderr/exit, parses JSON, and returns the result. Sandbox-bound tools (forge_runner, payload_swarm, the seven crypto_* primitives, instrument_trace) execute inside one of the four hardened replicas.
  5. Real-time fanout. Orchestrator publishes structured messages (thought / tool_call / tool_result / hypothesis / vulnerability / chain suggestion / loop-break / plan-tree event) to Redis channel session:{session_id}. WebSocketManager listens on that channel and broadcasts to every WebSocket client connected to /ws/{session_id}. Frontend updates the live feed, hypothesis panel, findings tab, and Cytoscape graph in place — no polling.
  6. Persistence. Hypotheses and agent thoughts → MongoDB. Confirmed vulnerabilities (≥0.7 confidence) → PostgreSQL vulnerabilities table with severity, CVSS, exploit code, remediation. Cross-session memory of confirmed findings → Neo4j (Target / Host / Service / Finding nodes; CHAINS_INTO edges). Strategic post-session reflections → ChromaDB. Artifacts (pulled binaries, fuzz crashes, capture files) → MinIO from v3.0 onward.

AI Orchestrator internals

backend/app/services/ai_orchestrator.py is the core of GENESIS — the Claude tool-use loop that drives every session. It owns five concerns:

  1. Prompt assembly. System prompt = MYTHOS preamble + tool catalog (per-agent allowed set) + recent messages window. Cross-session memory (U4 technique recall + T8 reflections) and v3.0 plan-tree summaries (T11) are injected as user turns.
  2. Tool dispatch. For each Claude tool_use block, the orchestrator routes to MCPClient with mapped tool name and validated parameters, awaits the response (with per-tool timeout), and feeds the result back as a tool_result on the next turn.
  3. Hypothesis + vulnerability extraction. Every text block is scanned for the JSON contracts below; matched blocks are persisted, broadcast on Redis, and tracked in the per-session hypothesis journal (Mongo).
  4. Evidence gating. U1 evidence rule + blind-class rule + Haiku critic run before any finding leaves the orchestrator. A "confirmed" claim with empty evidence list is automatically demoted to "unverified". The Haiku critic can also dispute a passing claim.
  5. Loop discipline. Ring-buffer loop-breaker (U2), idle-stop guard (v3.0 exhaustive mode), creativity nudge after 6 stock-tool iterations, and FINAL_REPORT detection all live here.

Hypothesis JSON contract

Every working theory the AI maintains is structured. The orchestrator parses these blocks from the response stream, attaches them to the session's hypothesis journal, and uses the id field to link follow-up evidence. 

{
  "HYPOTHESIS": {
    "id": "h1",
    "statement": "I think /api/orders/:id is IDOR-vulnerable because the auth check is missing on this route",
    "confidence": 0.62,
    "evidence_for":     ["GET /api/orders/100 returned another user's order"],
    "evidence_against": ["The /api/users/* family did enforce auth"],
    "next_test": "Try POST /api/orders/100 with manipulated body to test write-side IDOR",
    "falsification_criteria": "If POST returns 403 with the same identity bypass, hypothesis is dead",
    "status": "active"          // active | confirmed | ruled_out
  }
}

When a hypothesis confirms with confidence ≥ 0.7 (and is not an environment-side hypothesis like "firewall blocked" or "target unreachable"), the agent must emit a matching VULNERABILITY block. v3.0 enforces this in the system prompt and back-stops it with a session-end Hypothesis → Finding bridge that auto-derives any missing rows from confirmed hypotheses.

Real-time channel — Redis pub/sub → WebSocketManager

The orchestrator is the single producer of session events; many frontend clients may consume them. To keep the design horizontally scalable, the orchestrator never writes to WebSockets directly. It publishes to a Redis channel named session:{session_id}; WebSocketManager subscribes per session and fans events out to all connected clients.

  • Producer: orchestrator emits thought, tool_call, tool_result, hypothesis, vulnerability, chain_suggestion, loop_break, plan_tree_seeded, plan_replan, artifact_pulled, graph_delta.
  • Channel: session:{id} on Redis. Multi-replica backends can all subscribe; messages fan out per replica.
  • Consumer: WebSocketManager on each backend instance broadcasts to its connected clients at /ws/{session_id}.

Auth model

  • REST: X-API-Key header. Compared with timing-safe equality. Disabled when the API_KEY env var is empty (dev mode).
  • WebSocket: ?token=… query parameter (browsers don't send custom headers on WS handshake). Same timing-safe comparison.
  • Per-tenant (v6.0): RBAC + audit log (T142) wraps both above with role-attributed actions.

Tool registry & executor (MCP server)

The MCP server is the boundary between the AI's tool calls and the actual scanning fleet. Tools self-register with metadata — name, description, params schema (Zod) — and the executor spawns subprocesses (nmap, masscan, nuclei) or runs in-process TS/JS probes (idor_probe, cors_probe, jwt_probe, cache_probe, prototype_pollution_probe, the crypto_* family, graph_query, payload_swarm, forge_runner, fuzz_binary, symbolic_exec, instrument_trace, browser_session, render_and_see, cve_patch_pull, artifact_hunter, artifact_pull). v4 adds 51 new probes (T29-T79); v5 adds 41 (T80-T120); v6 adds 34 (T121-T154); v7 does not add tools — it adds reasoning loops above the existing tool layer.

Tier-1 (v1.0) — what shipped first

Before the AI-driven Tier-2 additions, the team spent a release cycle making the autonomous loop itself reliable. v1.0 is the foundation — five upgrades labeled U1 through U5 — and every later capability relies on its machinery. If you removed Tier-1, the AI would sometimes claim "confirmed" without evidence, get stuck retrying the same tool, record chains without ever acting on them, forget everything between sessions, and run multiple agents that ignored each other.

Analogy

Tier-1 is like installing guardrails, a notebook, and a telephone in the researcher's office. None of it is the work. All of it makes sure the work is honest, doesn't go in circles, doesn't disappear when they log off, and travels between teammates.

U1 Evidence rules & adversarial critic

Findings must prove themselves

Two rules now run in code, not in the prompt:

  • Evidence rule. A finding claiming "confirmed" or "exploited" must cite concrete evidence — a tool call that actually ran in this session, a callback hit, a quoted response diff. Empty list ⇒ automatically demoted to "unverified".
  • Blind-class rule. Blind bugs (blind SSRF, blind XXE, time-based SQLi, etc.) require either an OOB callback that fired, or — added in v2.0 — a passing Payload Forge oracle.

On top of those, an adversarial critic runs after every high-confidence finding: a smaller model (Claude Haiku) reads the claim and the evidence and votes confirmed / disputed. The critic can downgrade even findings that passed the deterministic rules if the cited evidence is vague.

U2 Loop-breaker

Stops the AI from spinning

The orchestrator keeps a small ring buffer of the last five tool-call signatures (tool name + a hash of its parameters). When the last three entries are identical, a "loop guard" user message is injected on the next turn. On the second such event in a session, the platform forces the AI to produce a final report. Loop-break events are visible as loop_break entries on the session's live feed.

U3 Active chain suggestions

Turns single findings into attack chains

Whenever a finding is saved with confirmed or exploited status, the platform checks the title against a keyword playbook. A match injects a follow-up suggestion onto the AI's next user turn. Example playbooks: SQLi → dump schema / find credentials / try --os-shell; SSRF → cloud metadata, internal services, gopher://; file upload → polyglots, LFI-to-RCE; JWT weak secret → mint admin token, kid header injection; GraphQL introspection → enumerate mutations.

U4 Technique recall (with negative signals)

Cross-session memory of what works

Per-technique cross-session memory in ChromaDB. For every confirmed finding the platform records the endpoint, canonical payload, tool, and a short technique tag (e.g. jwt-alg-none, cache-xfh-reflection, nosql-ne-boolean). At the start of a new session, top-K techniques from similar-fingerprint past targets are pulled back. Crucially, "didn't work" is also recorded — unverified and disputed rows become negative signals so future sessions deprioritize known dead ends.

U5 Multi-agent messaging

Parallel agents that actually cooperate

U5 ships two channels:

  • PRIOR_PHASE_FINDINGS seed. Between Phase 1 and Phase 2, structured Phase-1 findings (open ports, live endpoints, detected stack, WAF verdict) are injected as a seeded user message at the start of Phase 2.
  • Shared findings bus. Each agent publishes key findings to a per-session Redis list (genesis:session:{id}:shared_findings, capped at 200 entries with a 2-hour TTL). Every agent reads fresh entries at the top of each iteration.

Tier-2 (v2.0) — AI Discovery

Earlier versions were mostly a smart orchestrator on top of standard scanners. Tier-2 changes that. The AI now writes exploit requests itself, pulls binaries off the target and reads them, runs custom scripts in a sandbox, looks at rendered pages visually, reads the fix for a CVE to understand the bug, and carries strategic lessons across sessions.

T1 Target Intent Brief

Thinking before acting

Before any tool runs, the AI takes a few thousand tokens of extended reasoning and produces a structured "brief": predicted tech stack, attack-surface hypotheses, vulnerability classes likely to exist, artifacts worth hunting for, payload seeds, and expected dead ends. The brief is saved (you can inspect it) and injected as the starting point of the main loop.

T2 AI Payload Forge

Writing the exploit itself

The AI uses ai_request_forge to write the full HTTP request — method, URL, headers, body — by hand. Alongside it, it declares an oracle: status 500 with body containing psycopg; response time greater than 8000 ms; body must contain a planted token; body length differs by more than 200 bytes between baseline and attack. A passing oracle counts as genuine evidence and satisfies the blind-class rule.

T3 Artifact Hunter & Pull

Finding and grabbing binaries and source

T4 Binary Decompiler & Code Reader

Reading the software it pulled

T5 Sandbox Runner

Writing and running its own scripts

The AI attaches an oracle; a pass counts as evidence under the same rules as Payload Forge.

Seeing the UI, not just the HTTP

Reading the fix to understand the bug

Tier-6 (v4.0) — Novel-Vulnerability Research Platform (now shipping)

Deployment status

v4.0 has been deployed and is now shipping. Every block in this chapter (T29-T79) — the novelty engine, the parser-differential probes, the HTTP-modern probes, the deserialisation gadget arsenal, upload + SSRF expansion, state-aware fuzzing, auth depth, browser-side / DOM probes, template / DB / LDAP depth, DoS / algorithmic complexity, the LLM / agentic-endpoint pack, non-HTTP service probes, and the AD / Kill-Chain wave — is live in the deployed platform. The v4.0 capability is not a roadmap anymore; it is the floor for everything v5+ builds on top of.

v3.0 finds signature-shaped bugs well — bug classes that have been described publicly. The bugs that win bug bounties and become CVE-of-the-year aren't signature-shaped. They live at the seams between two parsers that disagree, between two states an application should be reachable in only one order, between a new protocol layer and the back-end's older assumptions, or in entirely new surfaces (LLM-backed apps) no scanner is mature enough to address. v4.0 closed that gap by making GENESIS a differential-testing platform first and a probe arsenal second.

v4.0 thesis in one sentence

Most novel vulnerabilities are differential bugs — they live where two implementations of the same idea disagree. v4.0 makes GENESIS a differential-testing platform first, and a probe arsenal second.

Four machinery gaps that block novel discovery

1. No HTTP-layer coverage feedback

When GENESIS fuzzes a binary it uses AFL-style coverage to steer payloads toward unreached code. When it fuzzes HTTP it is blind. Coverage feedback is the single biggest multiplier for novel bug discovery; without it, the swarm produces variation toward random bytes instead of unhit code paths.

2. No HTTP-layer differential testing

fuzz_differential exists for binaries; nothing equivalent for HTTP. Yet every famous parser-confusion CVE of the last five years was discovered by spotting a parser disagreement.

3. No state-machine model of the target

The agent reasons step-by-step but never builds an explicit FSM of the target's flow. Multi-step business-logic bugs (skip a step, repeat a step, run two in parallel) are the most lucrative class on the modern web.

4. Anomaly detection is shape-only

payload_swarm's novelty score is a hash of length-bucket + exit-code + head/tail bytes. Catches structural anomalies but misses semantic ones — different internal phrasing, an error message that hints at a bug class.

Tier-7 (v5.0) — Zero-Day Discovery Platform

Every prior version of GENESIS is an exercise in recognising bugs. The system gets better at finding bugs that someone, somewhere, has already named. v5.0 is the version where GENESIS starts imagining — reasoning about a target from first principles, proposing a bug class that has never been documented, designing an experiment to test it, and confirming it.

v5.0 thesis in one sentence

The platform that finds 0-days is not the one with the most probes — it is the one that reads source code, reasons over invariants, debates itself adversarially, and builds new tools when the existing ones aren't enough.

Five failure scenarios v3 + v4 cannot handle

Scenario A — logic flaw only visible in source

A SaaS billing platform's applyDiscount() checks uses_remaining, decrements, applies — three SQL statements without a transaction. A skilled attacker reads this in leaked source and exploits the race. v4's flow_fuzzer fires concurrent requests blindly but has no way to know the three-statement structure exists.

Scenario B — bug class is genuinely new

Target uses an LLM to translate user input into SQL. Nobody has documented "LLM-translated SQL injection via prompt-shape" yet. Every probe in v4 is for a known class.

Scenario C — proprietary protocol behaviour

Target speaks a custom binary protocol over WebSockets. v4's grpc_probe and mqtt_probe don't apply. v3's fuzz_binary needs a corpus and a binary. Without learned grammar the agent cannot fuzz meaningfully.

Scenario D — multi-day reasoning chain

Day 1: low-sev info disclosure (admin email). Day 4: medium SSRF. Day 10: a CVE drops in a library the target uses. The chain is the bug — each piece is too low to act on alone, but together they're a critical RCE.

Scenario E — the agent needs a tool that doesn't exist yet

Target uses a custom HMAC scheme over an exotic encoding. None of v4's 100+ tools fit. The agent writes a one-off forge_runner script — runs once, dies, no record, no reuse.

Tier-9 (v7.0) — Reasoning Architecture & Custom Loops

Across v3 + v4 + v5 + v6, GENESIS specifies ~120 capability blocks. Counting honestly: ~85% of those are tools, integrations, UX, ops; ~10% are custom reasoning architecture; only ~5% is custom model work. That last 5% is exactly what separates Mythos from GENESIS-on-Opus. v7.0 corrects this by deliberately not adding any new MCP probes — all twelve T-blocks are reasoning loops.

v7 thesis

A loop that compresses a 10,000-token reasoning task into ten 1,000-token turns lets a generic Opus model reach conclusions a 10x more capable monolithic model would be needed to reach in a single turn. Loop structure substitutes for reasoning depth within the loop's domain.

Tool vs reasoning loop

Concrete example — composing a ROP chain
Tool approach (v5/v6 T108): a "rop_chainer" tool searches binary for gadgets, returns a ranked list. The LLM reads the list and asks: "given these 47 gadgets, build a chain that calls execve and fits in 200 bytes." The model handles all constraint reasoning, gadget composition, and budget arithmetic in a single forward pass with no scratch space.
Reasoning loop approach (v7 T155): the loop runs gadget search → constraint propagation → register-state simulation → byte-budget check → gadget re-search if over budget → iterate. The model is the controller, but the loop holds the working memory. Each turn is small and tractable; the loop's structure compensates for the model's bounded reasoning span.

The AlphaZero analogy

AlphaZero plays go better than any human despite having a neural network that, on its own, would be merely strong-amateur level. The trick is the combination: MCTS explores branches + the network evaluates each branch. The search structure does most of the heavy lifting; the network does cheap evaluations. Every v7 loop is built on this template — the loop is the search structure; the LLM is the evaluator.

Tier-10 (v8.0) — Custom Models & Training Flywheel

v7 builds reasoning loops; v8 trains the models inside them. Where v7 compresses search space so Opus can match larger systems within a domain, v8 grows the models themselves through a closed-loop training flywheel: every confirmed finding becomes training data, training data fine-tunes specialists, fine-tuned specialists find more findings.

v8 thesis

Mythos's reasoning depth comes from training on real exploit corpora at scale. We can't replicate that scale. But we can build a flywheel where every confirmed GENESIS finding becomes training data, every fine-tune produces a slightly better specialist, and every better specialist produces more confirmed findings. The flywheel grows the model the platform deserves over time.

The training flywheel

  1. Confirmed bug. Any session produces a confirmed finding with cited evidence.
  2. Corpus ingestion (T167). Daemon ingests it into a structured (target_class, vulnerability_pattern, exploit_attempt, outcome, citations) tuple.
  3. Counterexample mining (T168). For the same target_class, mines near-miss code that is not vulnerable — contrastive labels.
  4. Quality gate (T170). High-impact tuples reviewed by humans; rest auto-accepted.
  5. Specialist fine-tune (T171). Per-specialist LoRA pipeline triggers when corpus delta exceeds threshold.
  6. Reward-model update (T172). Reward model re-trained on success/failure labels.
  7. Continual deployment (T174). Updated specialists ship with drift-checks; v6 T154 monitors health.
  8. Better specialists find more bugs. Loop continues.

Theme α — Training-data flywheel (T167–T170)

T167

exploit_corpus_curator (always-on daemon)

Ingests every confirmed GENESIS finding, every successful forge_runner script, every public CVE patch + PoC, every adversarial-debate convergence, every invariant-violation. Normalises into structured tuples. Stored in the new versioned, partitioned Training Corpus.

T168

counterexample_miner

For every confirmed-vulnerable code pattern, mines near-miss code that is structurally similar but not vulnerable. Provides contrastive labels — the difference between brittle and useful fine-tunes.

T169

synthetic_data_generator

Uses v6's replica spawner (T122) to programmatically inject known bug patterns into clean code, generating labelled training data at scale. Bug patterns: SQLi sinks, missing auth checks, race conditions, integer overflows, deserialisation sinks.

T170

corpus_quality_gate

HITL review queue for high-impact training examples. Examples with high uncertainty, novelty, or importance get queued for human verification. Rest auto-accepted on lower bar. Mandatory immune system — a single mislabelled "this is exploitable" example poisons every subsequent fine-tune.

Theme β — Specialist fine-tuning (T171–T174)

T171

per_specialist_lora_pipeline

Per-specialist LoRA fine-tuning on partition-specific corpus. Crypto / auth / kernel / web / IoT / mobile / OT / embedded specialists each tune on their domain. LoRA adapters are ~300MB each vs 200GB for a full model — cheap to train, deploy, swap.

T172

reward_model_exploit_success

Small classifier predicting P(exploit_succeeds | target, vulnerability_candidate, exploit_attempt). Used by v7's loops as a ranker — higher P gets sandbox time first. Inspired by AlphaZero's value network.

T173

distillation_pipeline

Distils specialist behaviour into smaller, faster models. Crypto-Opus-LoRA → crypto-haiku-distilled. High-throughput screening at low cost — big models for deep reasoning, small models for breadth.

T174

continual_learning_loop

Combines T154 drift-detection + T167 corpus + T171 fine-tunes into a closed continual-learning system. Confirmed bugs flow into corpus daily; specialist re-tunes weekly; drift-controlled rollout; auto-rollback on drift signal.

Theme γ — Mythos integration & portfolio routing (T175–T178)

T175

t13_conformance_test_suite

Validates that every existing agent / specialist / loop produces structurally identical outputs when the underlying model swaps from Opus to Mythos to a custom fine-tune. Battery of contract tests run on every PR.

T176

mythos_ab_harness

Runs identical engagement scenarios with (a) raw Mythos API calls and (b) GENESIS-orchestrated Mythos. Measures bug yield, time-to-first-bug, exploit quality, false-positive rate, cost. The killer demo: empirical data that GENESIS-on-Mythos > raw Mythos because of evidence enforcement and tool amplification.

T177

model_portfolio_router

Routes per-task to the right backend in the registry. Decision factors: required reasoning depth (deep → Opus or Mythos; shallow → distilled small), latency budget, cost ceiling, task domain. The most important block in v8.

Concrete walk-through

A session contains: surface scan (1000 calls — distilled small); fingerprinting (50 — distilled small); hypothesis formation (200 — Opus); ROP-composition loop (12 — Mythos when available else Opus); evidence summarisation (5 — distilled medium). Total cost 1/8th of "everything Opus" with quality matching on calls that need it.

T178

closed_loop_improvement

The flywheel itself — wires T167 corpus + T171 fine-tune + T172 reward-model + T173 distillation + T174 continual-learning + T177 router into a single self-improving system. After 6-12 months the corpus contains a private offensive-security training set no other security platform has access to. The moat.

How findings are verified

A finding marked confirmed or exploited in the report has been through these gates:

  1. Evidence rule (U1). Concrete evidence cited or auto-demoted to unverified.
  2. Blind-class rule (U1). OOB callback or passing oracle required.
  3. Critic pass (U1). Haiku reads claim + evidence and votes.
  4. Hypothesis confirmation rule (v3.0). ≥0.7 confidence on a target-side hypothesis must emit a matching VULNERABILITY block.

What GENESIS can't do

  • No destructive actions. Run on targets you can restore.
  • Not a replacement for a human auditor. Use the report as a starting point.
  • No kernel, firmware, or hypervisor analysis in v3.0. v5.0 T114 + T139/T140 + Tier-4 T15 close this.
  • No browser-engine zero-day in v3.0; would need instrumented harnesses.
  • Memory-corruption exploitation is partial. v3 T9/T10 find crashes and prove reachability; v5 T106-T109 + v7 T155/T158 + v8 T172 are needed for autonomous weaponisation on hardened targets.
  • Frontier-model ceiling. No amount of scaffolding lifts a model above its reasoning ceiling. T13 is the path to raise that ceiling.

Rules of engagement

You are responsible

GENESIS has no authorization check built in. Don't run it against systems you don't own or haven't been explicitly authorized to test.

  • Use a dedicated, isolated target-lab network (the compose file sets up vuln-lab).
  • Don't aim it at production without a change window, rollback plan, and the owner's written consent.
  • The sandbox runner is isolated, but an AI-written script is still code you authorized. Read what it's doing on the session viewer.
  • Keep your Anthropic API key out of version control — stored encrypted, redacted in the UI.
  • v6.0 onward: the OT/ICS specialist (T139) ships with default-deny actuator policy. Persistence/C2 (T79) is opt-in. Persona orchestrator (T135) generates impact-maximising hypotheses — keep against replicas only.

Data & privacy

  • All session data lives on your own machine (Postgres, Mongo, Redis, Chroma).
  • Target artifacts (pulled binaries, source trees) live in a Docker volume scoped per session.
  • AI calls go out over HTTPS to Anthropic. Your target payloads and tool outputs are sent as context. Check policy before sensitive scans.
  • The only data persisting across sessions is the intelligence library — technique hashes, strategic reflections, fingerprints. Wipe via the ChromaDB volume.

Multi-tenant boundaries (v6.0+)

  • Hierarchy: org → team → project. Per-tenant Neo4j namespace, Postgres schema, sandbox quota, LLM-token budget (T141).
  • RBAC roles: operator, reviewer, admin, read-only. Every action attributed (T142).
  • Audit log: append-only, immutable, queryable for compliance (T142).
  • Event log: replay-able session history (T146); ML researchers can A/B new agents against historical sessions.
  • Compliance reports: PCI-DSS, HIPAA, SOC 2, ISO 27001, NIST CSF, NIST 800-53, OWASP ASVS templates (T144).

Troubleshooting

"LLM test connection failed"

Check the API key, provider (Anthropic vs Azure vs Bedrock vs custom — T13 hook), and that your machine can reach the endpoint. On Azure, ensure the URL does not include the /v1/messages suffix.

Session stuck on "Iteration 0"

Almost always the first AI call failed. Open the Errors tab — typically a 401, 400, or network error.

"Scan failed without running any tool"

Look at the Errors tab for phase target_brief. If pre-scan reasoning errored, the loop falls back to the old seed and runs.

Chromium renderer crashes on memory

768 MB cap. A very JS-heavy page can blow it; the render returns an error but the session continues.

Ghidra container takes forever on first run

First-time decompilation takes minutes. Subsequent calls for the same file (by hash) are cached.

Sandbox says "timed_out: true"

The script hit the 60 s wall-clock limit. Either an infinite loop or a slow target.

Loop-breaker fires too often (v3.0+)

The plan tree (T11) should be reducing this. Check the Activity tab for plan_tree_seeded. If absent, the brief failed and the loop is operating without strategic context.

payload_swarm returns no novelty >0.5 (v3.0+ / v4.0+)

Either the variants are too similar (the agent should diversify) or the target is too uniform (the response signature collapses everything to one bucket). v4.0 T30 + T31 widen the signature space.

Replica spawner failed to scaffold (v6.0)

Either T121 fingerprint confidence was below threshold (target is genuinely opaque) or the matched OSS components have license / image-pull issues. Check the Containers tab for the replica_pool service.

Reasoning loop dead-ends after N turns (v7.0)

Loop-state store keeps the trail. Inspect via the Loops tab in the Session Viewer; common causes are budget exhaustion or constraint propagation pruning all branches.

Specialist drift detected (v6.0/v8.0)

T154 fired — the specialist's predictions deviated from baseline. T174 auto-rollback to the last green checkpoint, then alerts MLOps. Check the model registry for active version vs deployed version.
