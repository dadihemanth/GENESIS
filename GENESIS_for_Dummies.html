About This Book

Welcome to GENESIS for Dummies. This book introduces an autonomous security platform called GENESIS to readers who don't (yet) want to wade through the comprehensive technical manual. Whether you're a security engineer kicking the tires, a curious operator who just inherited a deployment, or a CISO who needs to explain to leadership "what does this thing actually do," you're in the right place.

GENESIS has shipped in eight major editions (the team calls them tiers): v1.0 through v3.0 are running today, and v4.0 through v8.0 are planned roadmaps. This book covers all eight — explaining the architecture, the autonomous loop, the hypothesis-driven thinking, every capability block, the safety guardrails, and how to actually use the thing on a Tuesday afternoon. We've left the hardcore JSON schemas and CSS variables for the comprehensive manual; here we focus on plain English.

T
Tip If you want the deep technical reference instead, see the companion file GENESIS_Manual_Comprehensive.html — same content, denser format, every T-block in full. This book is designed to be skimmed.

Foolish Assumptions

This book assumes that you:

  • Have used a computer and at least one web browser.
  • Roughly understand what a web application is — something at a URL like https://example.com that responds when you click things.
  • Know that vulnerabilities are software flaws attackers can exploit (SQL injection, leaked credentials, the Heartbleed bug, etc.).
  • Are comfortable with the terminal, or at least willing to run a few commands when prompted.
  • Are operating against targets you have permission to test — your own infrastructure, a contracted engagement, a CTF range, or a bug-bounty program with you on scope.

This book does not assume that you:

  • Have shipped your own scanner.
  • Know what a "ROP gadget" is. (We'll explain — see Chapter 13.)
  • Have ever heard of LoRA fine-tuning. (Also covered — see Chapter 14.)
  • Are fluent in CSS, MCP, or three database vendors at once.

Chapter 1: What the Heck Is GENESIS?

In this chapter
  • Meeting your new junior security researcher — who never sleeps, never tires, and never forgets
  • Understanding the difference between a scanner and an autonomous AI security platform
  • Knowing when GENESIS is the right tool — and when it isn't

GENESIS is a program you point at a target — a website, an IP address, a hostname you own — and it tries to find security weaknesses in it. Then it writes them up. In a report. With evidence. Then it goes home.

The clever bit is the brain: GENESIS uses Anthropic's Claude as the reasoning engine, surrounded by a fleet of standard security tools (Nmap, Nuclei, SQLMap, etc.) and a growing collection of custom probes (a binary decompiler, a headless browser, a sandboxed script runner, a 4-replica payload swarm, an attack graph). The brain decides what to do next, reads what comes back, forms a picture of the target, and keeps going until it has a report.

Plain-English analogy

Think of GENESIS as a junior security researcher you can hire for a few hours. You give them a website to assess. They open a laptop, take notes, run some standard tools, read the output, form guesses about where the weak spots might be, test those guesses, and write up what they find. GENESIS does that — except the "laptop" is a fleet of containers, the researcher never gets tired, and they remember every target you've ever scanned.

Wait — isn't that just a scanner?

No. Scanners run a fixed list of checks. GENESIS does five things scanners don't:

  • Forms hypotheses before testing. "I think the /admin path is interesting because the response leaks the framework version." Then it designs an experiment to confirm or refute that idea.
  • Writes its own exploits. When the canned scanners don't fit, the AI authors a custom HTTP request, declares what proof would look like (an "oracle"), and either passes or fails honestly.
  • Reads code it pulled. If the target leaks .git or a sourcemap, GENESIS pulls it and the AI literally reads the source for hardcoded secrets and weak crypto.
  • Remembers across sessions. Confirmed findings, dead-end techniques, strategic lessons — all stored and recalled when a similar target comes up next time.
  • Has falsification rules. The platform won't let the AI claim "confirmed" without evidence. There's a second AI (Claude Haiku) that disputes weak claims.
R
Remember GENESIS isn't a magic 0-day finder. It's an autonomous agent that does what a junior security researcher would, with a defined process. It still produces occasional false positives, still misses bugs only humans would notice, and still depends on you giving it a target you're allowed to test.

When is GENESIS the right tool?

You should use GENESIS for…Don't use GENESIS for…
Internal security teams testing their own appsScanning systems you don't own without written permission (illegal in most places)
Penetration testers under contract"Stress testing" a competitor's site (don't)
Bug-bounty researchers on scopeProduction systems without a change window and rollback plan
Red-team exercises and CTF training rangesAnything where a destructive payload could cause physical harm (industrial control systems, medical devices)
Pre-launch security checks on stagingSole authority on whether to ship — always have a human review the report
!
Warning GENESIS does not check authorization. There is no "are you sure?" dialog. If you point it at a target you're not allowed to test, the legal consequences are on you. Read Chapter 18 (Rules of Engagement) before you point this thing anywhere.

Floors 1-4 are open for business; floors 5-8 are still under construction (planning stage), but the foundations and steel for them are laid.

  • Floor 7 (v7.0) Reasoning Architecture — Tier-9 — twelve specialised reasoning loops that compress search space so a generic LLM can match much larger systems.
  • Floor 6 (v6.0) Sophistication & Blackbox 0-Day — Tier-8 — replica spawning, curiosity-driven RL, real-time threat intel, multi-persona adversaries, production-grade engineering.
  • Floor 5 (v5.0) Zero-Day Discovery — Tier-7 — source-aware reasoning, adversarial agent debate, self-improving tooling, long-horizon Researcher agent.
  • Floor 4 (v4.0) Novel-Vulnerability Research — Tier-6 — differential testing, coverage feedback, 51 new probes spanning parser quirks, HTTP modern, deserialisation, LLM endpoints, AD lateral movement.
  • Floor 3 (v3.0) Cross-session reasoning — Tier-5 — Neo4j attack graph, 5 specialist agents, parallel sandbox swarm, 10-tab session viewer.

  • Floor 1 (v2.0) AI Discovery — Tier-2 — payload forge, artifact pull, Ghidra decompilation, sandbox runner, vision, CVE patch reader, session reflections.

Chapter 3: Getting GENESIS Up and Running

In this chapter
  • Reviewing the basic prerequisites (Docker, an Anthropic API key, and a target you're allowed to test)
  • Spinning up the full container fleet via Docker Compose
  • Configuring your API key and running your first sanity scan

Prerequisites

You'll need:

  • Docker + Docker Compose. GENESIS ships as a fleet of containers. Compose orchestrates them.
  • An Anthropic API key. Get one at the Anthropic console. Without it, the AI part doesn't run.
  • A target you have permission to test. A vulnerable training app like DVWA or Juice Shop is great. Or your own dev environment.
  • Disk space. The full v3.0 fleet (13 containers including Ghidra, AFL++, angr, Chromium, four sandbox replicas) is around 8-10 GB.
  • Memory. 8 GB minimum, 16 GB comfortable. The Chromium and Ghidra containers are memory-hungry.

The basic dance

From the project root, the typical bootstrap sequence is:

git clone <the repo>
cd GENESIS
cp .env.example .env
# edit .env to set your ANTHROPIC_API_KEY (or do it later in the UI)
docker compose up -d
# wait ~60 seconds for Postgres / Mongo / Neo4j / Chroma to come up healthy
open http://localhost:3000
T
Tip You can leave ANTHROPIC_API_KEY blank in .env and set it instead in the Settings page of the running UI. The UI version uses the same encrypted-at-rest store that the API uses; it's redacted on display so you can't accidentally screenshot it.

What's actually running

If you run docker compose ps after a successful start, you'll see something like:

Warning The first time you bring up the fleet, image pulls can take a while (Ghidra alone is ~2.5 GB). Don't kill the compose run — it's not stuck, it's downloading. Subsequent restarts are fast.

Your first scan

  1. Open http://localhost:3000.
  2. Settings → enter your Anthropic API key. Click "Test Connection" — should be a green check.
  3. Dashboard → "Start New Session". Type a target — for a first scan, point it at http://localhost:8080 if you've spun up DVWA or Juice Shop alongside.
  4. Pick a profile. Fast is good for a first sanity check. Deep is the realistic default. (v3.0+ defaults every scan to Exhaustive with idle-stop.)
  5. Click Start. Watch the live feed. Findings appear in the Findings tab as they're confirmed.
  6. When the session ends (or you stop it), download the Markdown report.
R
Remember AI calls cost money. A Deep scan against a non-trivial target can run a few dollars of Anthropic API spend. Set a budget alert in the Anthropic console before you start firing scans against everything you can think of.

Chapter 4: The Architecture, Demystified

In this chapter
  • Picturing GENESIS as three rooms — Frontend, Backend, MCP Server — with hallways between them
  • Understanding how a single click in the UI travels all the way to a Nmap scan and back
  • Knowing why the architecture is "polyglot" and why that's not just buzzword bingo
Plain-English analogy

Imagine three rooms connected by hallways. Room 1 is the lobby (Frontend) where the operator stands. Room 2 is the office (Backend) where the AI brain reads reports and gives instructions. Room 3 is the workshop (MCP Server) where the actual tools — drills, scanners, decompilers — live. The lobby never goes directly to the workshop. Every request from the lobby walks to the office; the office decides what tool the AI wants; the office walks to the workshop; the workshop runs the tool and walks the result back to the office; the office thinks about it and walks an update back to the lobby. The lobby just watches the live feed and clicks buttons.

The three rooms

  • Frontend (Room 1, port 3000): A React web app. Pages for Dashboard, Sessions, Vulnerabilities, Tools, Attack Graph. Talks to the Backend via REST and a WebSocket. That's it.
  • Backend (Room 2, port 8000): A Python FastAPI service. Runs the AI Orchestrator (the loop calling Claude). Owns session lifecycle. Manages the WebSocket. Talks to all the databases.
  • MCP Server (Room 3, port 3001): A Node.js Express service. Hosts the registry of 100+ scanning tools. The Backend POSTs to /tools/execute; the MCP Server runs the tool (or spawns a subprocess) and returns the result.

The data flow, step by step

  1. You click "Start New Session" in the Frontend. The Frontend POSTs to /api/v1/sessions with the target.
  2. The Backend creates a session row in PostgreSQL and kicks off the AI Orchestrator.
  3. The Orchestrator builds a prompt with: the system prompt ("you are an autonomous red-team operator"), the tool catalog, any cross-session memory, and the current state.
  4. It calls Claude. Claude responds with either a tool call ("run nmap on the target") or a hypothesis / vulnerability block.
  5. If a tool call: the Orchestrator HTTP-POSTs /tools/execute on the MCP Server. The MCP Server runs nmap (or whatever), captures the output, returns JSON.
  6. The Orchestrator publishes the tool call and result on a Redis channel session:{your_session_id}.
  7. The WebSocketManager (also in the Backend) is subscribed to that Redis channel. It broadcasts the event to every WebSocket client watching this session.
  8. Your Frontend sees the event arrive on the WebSocket and updates the UI in place — no polling.
  9. Repeat steps 3-8 until the AI says "I'm done" (FINAL_REPORT) or the loop-breaker forces a wrap-up.
TS
Technical Stuff Why Redis pub/sub instead of the Backend writing directly to WebSockets? Because in production you want multiple Backend replicas behind a load balancer. The Orchestrator might be on Backend instance A; the operator's WebSocket might be connected to instance B. Redis is the shared memory that lets B see what A is doing. It also makes the design replay-able for v6.0's event sourcing.

Why polyglot persistence?

GENESIS uses five (eventually more) databases, each chosen because it's the right shape for one specific job. This isn't over-engineering — it's using the right tool for the right thing:

  • PostgreSQL stores the report. Sessions, vulnerabilities, settings, users — relational data with strict schema and foreign keys.
  • MongoDB stores everything that varies in shape — agent thoughts, hypothesis journals, raw tool outputs. JSON-shaped, sometimes huge, rarely needs joins.
  • Redis is the postal service. Live-feed events flow over it. The shared findings bus between agents lives in it.
  • ChromaDB answers "have we seen something like this before?" — vector embeddings for technique recall and session reflections.
  • Neo4j (v3.0+) answers "what attack chains exist?" — a graph of Targets, Hosts, Services, Findings, and how they connect.
  • MinIO (v3.0+) stores big files (pulled binaries, fuzz crashes) so any worker on any host can fetch them.
T
Tip You can wipe ChromaDB to start GENESIS's "memory" from scratch — useful when testing a clean comparison, or when ChromaDB's embeddings drift away from useful recall.

Chapter 5: How GENESIS Thinks

In this chapter
  • Understanding hypothesis-driven testing — the heart of how GENESIS reasons
  • Meeting "oracles" — the secret sauce that lets the AI prove its own claims
  • Seeing the evidence rules and the adversarial critic that prevent the AI from grading its own homework

The hypothesis loop

Most scanners work on a "fire and forget" model: try check N, see if it failed, move to check N+1. GENESIS works differently. It has to write down what it thinks is happening before it tests anything. The structure is always:

  • Statement: "I think endpoint /api/orders/:id is IDOR-vulnerable because the auth check looks missing."
  • Evidence for: Things observed that support the idea.
  • Evidence against: Things observed that argue against it.
  • Next test: What it'll do to prove or disprove the idea.
  • Falsification criterion: The specific result that would kill the hypothesis.
  • Status: active / confirmed / ruled_out.
Plain-English analogy

A doctor doesn't randomly run every test on every patient. They form a working diagnosis, design tests that would prove or disprove it, run the test, update the diagnosis. GENESIS does that — and the "diagnosis" (the hypothesis) is written down where you can read it.

What's an oracle?

When the AI writes a custom HTTP request via the Payload Forge or a custom script via the Sandbox Runner, it has to declare alongside it what success would look like. That declaration is the oracle. Examples:

  • "Expect status 500 and body must contain psycopg" — proves the database threw an error from a SQL injection.
  • "Response time greater than 8000 ms" — proves a time-based blind injection.
  • "Body must contain this unique token I planted" — proves reflection.
  • "Body length must differ by more than 200 bytes between baseline and attack" — proves boolean blind injection.

The platform sends the request, runs the oracle, and reports pass / fail / partial. The AI doesn't get to grade itself.

The evidence gate (U1)

Before any finding leaves the orchestrator with verification status "confirmed" or "exploited", three rules run in code (not in the AI's prompt):

  1. Evidence rule. Concrete evidence must be cited. Empty list → automatic demotion to "unverified".
  2. Blind-class rule. Blind bugs (blind SSRF, blind XXE, time-based SQLi) require an OOB callback hit OR a passing oracle.
  3. Critic pass. A second AI (Claude Haiku, smaller and cheaper) reads the claim and the evidence and votes confirmed / disputed. The critic can downgrade even claims that pass the deterministic rules.
R
Remember The evidence gate is in code, not in prompt. The AI cannot talk its way around it. This is the single biggest reason a "confirmed" finding from GENESIS is more trustworthy than a confirmed finding from a one-shot LLM call.

The verification ladder

StatusMeaning
UnverifiedThe AI suggested this might be a problem but couldn't prove it. Worth a human look.
ConfirmedThe AI produced concrete evidence — quoted tool output, OOB hit, passing oracle.
ExploitedThe AI actually demonstrated the bug working against the target.
DisputedThe Haiku critic reviewed and decided the evidence doesn't hold up. Treat as false positive.

Chapter 6: Where the Data Lives

In this chapter
  • Visiting each of the five filing cabinets GENESIS keeps
  • Knowing what to look in when you want to answer a specific question
  • Discovering the new stores planned for v5, v6, v7, and v8
Plain-English analogy

Imagine an archivist with five filing cabinets. Each cabinet is for a different kind of document. The archivist knows: "If you want a contract, that's the legal cabinet. Lab notes? Yellow. Phone messages? Pink." Same idea here.

The five cabinets

  • Cabinet 1 — PostgreSQL. The official record. Sessions, vulnerabilities, settings, users. When the auditor asks "what did GENESIS find on this engagement?", you query PostgreSQL.
  • Cabinet 2 — MongoDB. The lab notebook. Agent thoughts (every reasoning step). Hypothesis journals. Raw tool outputs. Target Intent Briefs (T1). Plan trees (T11). Pulled artifact metadata (T3).
  • Cabinet 3 — Redis. The whiteboard. Live-feed channel session:{id}. Cross-agent shared findings list (with TTL). Ephemeral.
  • Cabinet 4 — ChromaDB. The "have I seen this before?" cabinet. Vector embeddings of past techniques (U4) and post-session strategic reflections (T8).
  • Cabinet 5 — Neo4j (v3.0+). The attack-graph cabinet. Targets, Hosts, Services, Findings, Credentials, with edges for LISTENS_ON, CHAINS_INTO, AUTHENTICATES_TO, GRANTS.

What v5+ adds to the archive

  • Vector store — semantic recall over the corpus of source / hypotheses / findings.
  • Property database — formal invariants per target inferred by T83.
  • Tool registry — self-synthesised tools (T97) get registered here.
  • Provenance store — the full reasoning trace per finding, for replay (T103).
  • Threat-intel store (v6) — CVE feeds + advisories ingested by T129.
  • Audit log (v6) — append-only, every action attributed to a person (T142).
  • Event log (v6) — replay-able session history (T146).
  • Loop-state store (v7) — intermediate states per reasoning loop (T160).
  • Training corpus (v8) — versioned, partitioned tuples that feed LoRA fine-tunes (T167).
T
Tip The Mongo collection hypothesis_journals is criminally under-explored. When a finding looks weird, open the journal for that session and read the hypothesis chain backwards from the finding. You'll often see the AI's reasoning in plain prose.

Chapter 7: Tier-1 Foundations (v1.0)

In this chapter
  • Meeting the five guardrails that keep GENESIS honest (U1 through U5)
  • Understanding why the reliability foundation came before any AI cleverness
  • Knowing why you'd never want to remove these even if you could
Plain-English analogy

Tier-1 is like installing guardrails, a notebook, and a telephone in the researcher's office. None of it is the work itself. All of it makes sure the work is honest, doesn't go in circles, doesn't disappear when the researcher logs off, and travels between teammates.

Five upgrades, all in v1.0:

  • U1 — Evidence rules & adversarial critic. A claim of "confirmed" must cite real evidence; the platform demotes empty claims; a second AI (Haiku) disputes weak ones.
  • U2 — Loop-breaker. If the AI calls the same tool with the same parameters three times in a row, the platform injects a "pivot or wrap up" nudge. Second time, it forces a final report.
  • U3 — Active chain suggestions. When a finding confirms, a keyword playbook injects a follow-up suggestion. SQLi → dump schema → try --os-shell. SSRF → cloud metadata, internal services. JWT weak secret → mint admin token.
  • U4 — Technique recall. ChromaDB stores per-technique memory: what worked AND what didn't. Future sessions on similar fingerprints inherit both.
  • U5 — Multi-agent messaging. A Redis findings bus + a "PRIOR_PHASE_FINDINGS" seed between phases means parallel agents actually share what they discover.
R
Remember Without Tier-1, every later edition's "confirmed" claim is just the AI's word. Tier-1 is what makes the report worth reading. It's invisible when it works, painful when it doesn't.

Chapter 10: v4.0 / Tier-6 — Hunting Bugs Nobody Has Seen

In this chapter
  • Grasping why v3.0 finds known-shape bugs well but misses the "wow" CVE-of-the-year class
  • Understanding the four machinery gaps that block novel discovery
  • Skimming the 13 implementation waves (T29 through T79) without trying to memorise all 51 probes

v3.0 is strong on bug classes that have been described publicly. The bugs that win bug bounties and become CVE-of-the-year aren't signature-shaped — they live at the seams between two parsers that disagree, between two states an application should be reachable in only one order, between HTTP/2's new semantics and the back-end's HTTP/1.1 assumptions, or in entirely new surfaces (LLM-backed apps) no scanner is mature enough to address. v4.0 targets these.

v4.0 thesis in one sentence

Most novel vulnerabilities are differential bugs — they live where two implementations of the same idea disagree. v4.0 makes GENESIS a differential- testing platform first, and a probe arsenal second.

The four machinery gaps

  1. No HTTP-layer coverage feedback. Binary fuzzing has it; HTTP fuzzing is blind.
  2. No HTTP-layer differential testing. No way to compare "edge" vs "origin" parser behaviour.
  3. No state-machine model of the target. Multi-step business-logic bugs are invisible.
  4. Anomaly detection is shape-only. Misses semantic anomalies (different phrasing, leak hints).

Chapter 13: v7.0 / Tier-9 — Teaching GENESIS to Think in Loops

In this chapter
  • Understanding why "more probes" stops being the answer at some point
  • Meeting the AlphaZero analogy that makes reasoning loops click
  • Touring the twelve domain loops (T155 through T166) that compress search space

Across v3 through v6, GENESIS specifies ~120 capability blocks. Counting honestly: ~85% are tools, integrations, UX, and ops. Only ~5% is custom model work, and ~10% is custom reasoning architecture. That last 15% is exactly what separates Mythos from GENESIS-on-Opus. v7.0 corrects this by deliberately not adding any new MCP probes — all twelve T-blocks are reasoning loops.

The AlphaZero analogy

AlphaZero plays go better than any human despite its neural network being merely strong-amateur on its own. The trick is the combination: a search structure (Monte Carlo Tree Search) + a network as a value function. The search does most of the heavy lifting; the network does cheap evaluations. Together they exceed what either could do alone. v7's reasoning loops are the search structure; the LLM is the evaluator.

Tool vs reasoning loop — the difference

Tool approach (v5/v6)Reasoning loop approach (v7)
Search binary for ROP gadgets, return ranked list of 47. The model reads the list and asks: "build a chain that calls execve and fits in 200 bytes." All constraint reasoning, gadget composition, and budget arithmetic in one forward pass with no scratch space.Loop: gadget search → constraint propagation → register-state simulation → byte-budget check → re-search if over budget → iterate. The model is the controller; the loop holds working memory. Each turn is small and tractable.

The twelve loops at a glance

  • T155 — ROP composition. Constraint-aware ROP chain assembly under byte budget.
  • T156 — Code intent (multi-zoom). Reads code at function → file → module → architectural levels.
  • T157 — Chain composer. Plans valid orderings of primitive vulnerabilities (KASLR-leak before write, etc.).
  • T158 — Heap layout. Allocator-aware heap shaping. Predict → execute → observe → refine.
  • T159 — Self-correcting exploit. Diagnoses why an attempt failed; proposes a corrected one. Most real exploits work on the third or fifth attempt, not the first.
  • T160 — Deliberation framework. The shared meta-architecture every other loop composes.
  • T161 — Tree-of-thought search. Branching exploration with explicit backtrack.
  • T162 — Long-context code harness. Reasoning over 1M+ token codebases via segment-summarise-recurse.
  • T163 — Cross-component invariant tracker. Tracks invariants spanning multiple files/services; flags inconsistencies as bug candidates.
  • T164 — Causal exploit trace. Builds causal graph from input bytes to side effects to downstream primitives.
  • T165 — Counterfactual exploration deep. "If we had a leak primitive, what attacks open up?"
  • T166 — Hypothesis decomposition. Breaks complex hypotheses into atomic, individually-provable claims.
TS
Technical Stuff Loops are slow. A 12-turn ROP-composition loop costs 12× as many tokens as a single-shot prompt. v8's portfolio router (T177) decides when the depth is worth the cost — and this is exactly why v7 + v8 compound.

Chapter 14: v8.0 / Tier-10 — GENESIS Goes to School

In this chapter
  • Understanding why "fine-tune our own specialists" closes a different gap than v7
  • Walking through the training flywheel: confirmed bug → corpus → LoRA → reward model → router
  • Comparing Path A (Mythos via T13) vs Path B (custom flywheel)

v7 builds reasoning loops. v8 trains the models inside them. Where v7 compresses search space so a generic Opus model can match larger systems within a domain, v8 grows the models themselves through a closed-loop training flywheel: every confirmed finding becomes training data, training data fine-tunes specialists, fine-tuned specialists find more findings.

v8.0 thesis in one sentence

Mythos's reasoning depth comes from training on real exploit corpora at scale. We can't replicate that scale. But we can build a flywheel where every confirmed GENESIS finding becomes training data. The flywheel grows the model the platform deserves over time.

The flywheel, in eight steps

  1. Confirmed bug. Any session produces a confirmed finding with cited evidence.
  2. Corpus ingestion (T167). Daemon ingests it as a structured (target_class, vulnerability_pattern, exploit_attempt, outcome, citations) tuple.
  3. Counterexample mining (T168). Mines near-miss code that's structurally similar but not vulnerable — contrastive labels.
  4. Quality gate (T170). High-impact tuples reviewed by humans; rest auto-accepted.
  5. Specialist fine-tune (T171). Per-specialist LoRA pipeline triggers when corpus delta exceeds threshold.
  6. Reward model update (T172). Predicts P(exploit_succeeds); used by v7 loops as a ranker.
  7. Continual deployment (T174). Updated specialists ship with drift checks.
  8. Better specialists find more bugs. Loop continues.

Path A vs Path B

PathWhat it isEstimated gap closure
Path A — Mythos via T13When access drops, swap the underlying model. v3-v8 platform amplifies it.~95% of Mythos-direct, plus deterministic evidence enforcement
Path B — Custom flywheelTrain our own specialists. Build training corpus. Distil and route.~30-50% of Mythos-direct on covered domains
R
Remember Path A and Path B aren't rivals. v8 builds both. Theme α + β are Path B; Theme γ is Path A integration prep. Run them in parallel; whichever path arrives first is the win.

What's a LoRA, anyway?

Plain-English analogy

Imagine a general practitioner spending their evenings on a cardiology CME course. Same doctor, refined cardiology depth. They didn't go back to medical school. They added a specialist module on top. That's a LoRA — a few hundred MB of fine-tuning instead of a 200 GB full-model checkpoint. Cheap to train, cheap to deploy, cheap to swap.

Tip T177 (the model portfolio router) is arguably the most important block in v8. Without it, you either burn money calling Opus on everything or starve quality calling distilled small everywhere. The router picks the right model per task. Most cost / quality / latency wins in production come from this single block.

Chapter 19: Verifying Findings Without Getting Fooled

In this chapter
  • Walking through a confirmed finding the way an auditor would
  • Spotting the three telltale signs of a hallucinated bug claim
  • Using the identification dialog and the Mongo journals as your audit trail

The auditor's walk-through

  1. Open the finding in the Findings tab.
  2. Click the row → identification dialog. Note the driving hypothesis.
  3. Read the cited evidence. Does it actually support the claim, or is it tangentially related?
  4. Find the tool call that produced the evidence. Re-run it manually if you can.
  5. If a passing oracle is cited, read the oracle predicate. Could it pass for a benign reason?
  6. Cross-check the affected service / endpoint against your asset inventory. Is this even your system?

The three telltale signs of a hallucinated finding

  • Evidence cites a tool that wasn't actually invoked. The Tools tab is the source of truth — if the cited tool doesn't appear there for this session, the AI made it up. (U1 should catch this; if it doesn't, file a bug against GENESIS itself.)
  • Oracle predicate is vague. "Response looks suspicious" is not an oracle. "Body length differs by >200 bytes" is.
  • Hypothesis statement contradicts evidence_against. Sometimes the AI lists evidence that should kill its own hypothesis and confirms it anyway. The Haiku critic should catch this; if you see it slip through, dispute the finding manually.
TS
Technical Stuff Every finding has a driving_hypothesis_id. You can pull the full hypothesis chain from MongoDB's hypothesis_journals collection (filter by session_id). Reading the chain backwards from the finding is faster than reading the Activity tab forwards.

Chapter 20: When to Doubt GENESIS

In this chapter
  • Knowing the things GENESIS just can't do (yet)
  • Recognising the smell of a confidently wrong AI answer
  • Calibrating your trust per finding type

Things GENESIS can't do (in v3.0)

  • Kernel, firmware, hypervisor analysis. v5 T114 + Tier-4 T15 close this.
  • Browser-engine zero-day — would need instrumented harnesses (Tier-4 T14).
  • First-class mobile (APK / IPA) analysis. v6 T138 closes this.
  • Memory-corruption weaponisation on hardened targets. v5 T106-T109 + v7 T155 work toward it; never trivial.
  • Anything model-gated — novel-bug intuition on unseen surfaces is bounded by the underlying model's reasoning depth. Path A (Mythos via T13) is the only way to lift it above Opus.

The smell of a confidently wrong answer

  • The hypothesis is plausible but the evidence is just one tool output that the AI is over-interpreting.
  • The finding cites a CVE that doesn't apply to the version actually deployed.
  • The exploit / PoC is a generic curl command without target-specific values filled in.
  • The remediation is suspiciously generic ("apply the latest security patches"). Real GENESIS remediations are specific.
R
Remember GENESIS is a starting point, not the final word. Use the report to focus human review, not to replace it. The platform's value is multiplying what one researcher can cover, not eliminating the researcher.

Chapter 21: Ten Common Mistakes Operators Make

In this chapter

  1. Pointing GENESIS at production without authorisation. The platform won't stop you. Get written consent. Always.

  9. Killing a session that's actually doing useful work. If the loop-breaker hasn't fired and the Findings tab is still incrementing, give it more iterations.
  10. Disabling evidence rules (U1) "to see what the AI says." You can't, technically, but operators sometimes turn down confidence thresholds and then trust the resulting noise. Don't.

  8. T28 payload_swarm. Use the Sandbox tab's filter "payload_swarm only". The novelty-scored variant ranking is the platform at its most original.
  9. T13 Model-swap hook. Try Anthropic API today, swap to Bedrock tomorrow. Same scaffolding, different engine. (T13 is shipping.)
  10. The Sessions page report export. Run any session, download the Markdown report, share it with a developer. The format alone changes the conversation.
