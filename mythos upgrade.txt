 Plan: GENESIS → Mythos-Level Autonomous Security Intelligence

 Context

 GENESIS currently runs a fixed 5-phase sequential loop (recon → service analysis → vuln scan → exploitation → reporting). Claude calls
 ~12 hardcoded tools in a predictable order. The result is a scripted scanner with an AI narrator, not a true autonomous agent.

 The upgrade makes GENESIS behave like "Claude Mythos" — an AI that reasons about a target, freely decides its own investigation path,
 chains discoveries into multi-step attack paths, generates working PoC exploit code, and accumulates intelligence across the session.
 The key technical pillars are: extended thinking, all 30 tools exposed, non-linear autonomy, attack chain correlation, and scan
 profiles.

 ---
 Architecture After Upgrade

 User selects scan profile → Session created → Celery dispatches Mythos Orchestrator
   └─ Extended Thinking loop (no fixed phases)
        ├─ Claude reasons deeply → calls any of 31 tools freely
        ├─ Thinking blocks saved to MongoDB as "deep_thoughts"
        ├─ Vulnerabilities extracted → attack_chain_id assigned
        └─ Post-session: AttackChainService correlates into kill chains
 Frontend: shows thinking blocks, attack chain graph tab, scan profile badge

 Step 1 — ai_orchestrator.py Full Rewrite

 1a. MYTHOS System Prompt

 Replace RESEARCH_SYSTEM_PROMPT with a prompt that:
 - Frames GENESIS as an autonomous threat intelligence engine, not a scripted scanner
 - Instructs Claude to reason about the attack surface holistically before acting
 - Requires multi-vector thinking: "what can I reach from this foothold?"
 - Demands exploit generation when a vuln is confirmed: working Python/bash PoC in exploit_code
 - Introduces attack chain concept: each vuln has a chain_id grouping related steps
 - Includes all 5 severity levels with CVSS anchors

 MYTHOS_SYSTEM_PROMPT = """You are GENESIS MYTHOS — an autonomous cyber-intelligence engine conducting a fully authorized security
 assessment.

 Target: {target}
 Session: {session_id}
 Scan Profile: {scan_profile}

 ## Core Directive
 You are not following a script. You reason about the target, form hypotheses, select tools, interpret results, and adapt. You chain
 discoveries: a discovered service leads to fingerprinting, which leads to a CVE match, which leads to exploit verification.

 ## Capabilities
 You have access to 31 tools spanning: port scanning, web crawling, DNS enumeration, SSL analysis, directory brute-forcing, injection
 testing, credential attacks, Windows/AD enumeration, static code analysis, and custom payload crafting.

 ## Attack Chain Thinking
 When you find a vulnerability, ask: "What does this enable?" Track exploitation paths as chains:
 - Chain 1: port 22 open → SSH banner → CVE-2023-XXXX → RCE
 - Chain 2: /admin exposed → default creds → authenticated SQLi → data exfil

 ## Vulnerability Output Format
 When you confirm a finding, emit a JSON block:
 {"VULNERABILITY": {"title": "...", "severity": "critical|high|medium|low|info", "cvss_score": 9.8, "cve_ids": ["CVE-XXXX-YYYY"],
 "affected_service": "Apache/2.4.49", "port": 443, "description": "...", "exploit_code": "#!/usr/bin/env python3\\n...", "remediation":
 "...", "confidence": 0.95, "attack_chain_id": "chain-1", "chain_position": 2, "verification_status": "confirmed"}}

 ## Scan Profile: {scan_profile}
 {profile_instructions}

 ## Rules
 - Never run destructive operations (no --delete, no data modification, no DoS)
 - Verify before reporting: don't report a vuln unless you've confirmed it with a tool
 - Generate real, working exploit PoC code where applicable
 - When you have fully assessed the target, output a FINAL_REPORT block and stop
 """

 Step 3 — New payload_crafter MCP Tool

 File: mcp-server/src/tools/payload_crafter.ts

 No binary needed. Pure logic tool — Claude calls it to get a curated payload list based on tech stack and vulnerability type. Returns
 structured payload arrays.

 Parameters:
 - vuln_type: sqli | xss | cmdi | lfi | ssrf | ssti | xxe | deserialization
 - tech_stack: detected technology (e.g., php, java, python, dotnet)
 - context: request context (e.g., GET param, JSON body, HTTP header)
 - encoding: none | url | base64 | html

 Returns: { payloads: string[], waf_bypass_variants: string[], detection_notes: string }

 Step 5 — New attack_chain.py Service

 File: backend/app/services/attack_chain.py

 Called after session completes. Groups vulnerabilities into kill chains by:
 1. Shared attack_chain_id (set by Claude during the session)
 2. Port/service proximity (vulns on same port → same chain)
 3. ChromaDB semantic similarity (search_similar_vulnerabilities)

 Returns structured chains:
 @dataclass
 class AttackChain:
     chain_id: str
     steps: List[Vulnerability]       # ordered by chain_position
     entry_point: str                  # first vuln title
     impact: str                       # last vuln severity
     exploitability: float             # avg confidence
     description: str                  # Claude-generated narrative

 New API endpoint in sessions.py:
 @router.get("/{session_id}/attack-chains")
 async def get_attack_chains(session_id: uuid.UUID, db: AsyncSession = Depends(get_db)):
     service = AttackChainService()
     return await service.get_chains(str(session_id))
