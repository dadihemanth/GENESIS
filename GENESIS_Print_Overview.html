1. What GENESIS Is

Plain-English definition

GENESIS is a security research assistant that plans tests, runs tools, studies the results, and writes findings with evidence.

Who uses it

Security teams, red teams, product security engineers, and leaders who need measurable proof instead of raw scanner noise.

What it improves

It reduces repetitive manual testing, connects related clues, and pushes the system toward proof-backed reporting.

What it is not

It is not a magic guarantee that every issue is found. It is an authorized assessment platform that still needs human judgment.

Main idea: GENESIS is valuable because it does not only ask "can we find something?" It also asks "can we prove it, deduplicate it, explain it, and give the owner a useful remediation path?"

6. Reading a GENESIS Report

Start with confirmed findings. These have passed the strongest evidence path available for that mode.
Check severity. Critical and high findings should have concrete proof and business impact.
Open the evidence. Look for tool output, response differences, screenshots, proof runs, or callback hits.
Review duplicates. If several findings have one root cause, fix the root cause once and retest.
Treat candidates as leads. Candidates are useful, but they are not final findings until promoted.
Use benchmark language carefully. Say "measured in this lab," not "finds everything everywhere."
Demo range interpretation: vulnerable app = target under test; patched twin = false-positive control; fake metadata service = proof canary for SSRF, not a normal vulnerable target.

7. The Scan Lifecycle

A GENESIS scan is not one giant scanner command. It is a repeated decision loop. Each round reads the current state, chooses the next best action, runs a tool or records a thought, then updates the evidence trail.

StageWhat happensPlain-English checkpoint
1. PrepareGENESIS loads target, scan profile, operator context, prior memory, and model routing.What are we testing, and what do we already know?
2. ReconAgents discover ports, services, apps, routes, technologies, and exposed artifacts.What doors, APIs, and clues exist?
3. HypothesizeThe system writes testable ideas such as "this endpoint may lack ownership checks."What weakness might exist, and what would disprove it?
4. TestTools run targeted checks, browser flows, custom requests, source queries, or sandbox proofs.Can we collect observable evidence?
5. ValidateEvidence rules and critic review support, refute, or downgrade weak claims.Does the evidence really support the claim?
6. DedupSimilar findings or candidates are grouped by root cause, endpoint, proof behavior, and likely fix.Is this one issue reported several ways?
7. Optional proofValidation Lab can add proof runs and promotion records for candidate leads.Would extra proof make this easier to trust?
8. ReportFindings, evidence, remediation, benchmark metrics, and reproducibility data are shown.What should the team fix first?
Important: GENESIS can discover quickly while still taking time to collect evidence and run critic review. Candidate proof work is optional follow-up, not a required bottleneck for every finding.

8. Reasoning Loops

A reasoning loop is a structured way for the AI to think through a hard problem in smaller steps. Instead of asking one model response to solve everything at once, GENESIS breaks a problem into ticks: consider options, choose one, record why, and continue until the loop completes or hits its budget.

Loop conceptSimple explanationWhy a reader should care
TickOne small reasoning step inside a loop.Shows the reader how the agent moved from uncertainty to a choice.
BranchAn option the agent considered.Shows alternatives, not just the final answer.
Chosen pathThe branch selected for the next step.Explains why GENESIS tested one path before another.
State snapshotThe loop's working memory at that tick.Makes complex reasoning replayable.
BudgetA limit on ticks and tokens.Prevents a loop from consuming unlimited cost.

Active loop types

LoopPlain-English purpose
code_intentReads a focused piece of code and explains what it is supposed to do.
invariant_trackerFinds rules the system normally follows and flags places that break those rules.
causal_traceTraces how one input or event leads to a later security-relevant outcome.
counterfactualAsks "what if this assumption were different?" to find alternate attack paths.
hypothesis_decompBreaks one vague idea into smaller claims that can be tested separately.
long_context_codeReads larger code areas by slicing the work into manageable pieces.
cross_file_compareCompares similar code patterns across files to find inconsistent behavior.
rop_compositionComposes low-level exploit building blocks in binary-analysis scenarios.
chain_composerConnects smaller findings into a realistic end-to-end attack chain.
heap_layoutReasons about memory layout when analyzing low-level memory bugs.
self_correctingClassifies why a proof failed, adjusts the attempt, and tries again within budget.
Why the Loops tab can be empty: loops fire when GENESIS calls the internal deliberate reasoning tool or when a profile/backstop nudges it to do so. A simple target may not need loops early. A deeper scan or a hard blocked hypothesis is more likely to show loop activity.

When loops usually appear

TriggerWhat GENESIS is trying to solveWhat the operator should do
Complex code or artifact evidenceThe agent needs to connect source, route, sink, and runtime behavior.Check whether the loop produced a clear next proof action.
Repeated uncertaintyThe agent has multiple possible explanations for the same observation.Look for branches that were rejected and why.
Coverage backstopThe session is drifting or has not used deeper reasoning after several rounds.Expect a loop to create a sharper plan or stop condition.
Proof failureA proof attempt failed but the hypothesis may still be valid.Confirm whether the revised plan is safer and more specific.
Cross-view mismatchEndpoint evidence and source evidence disagree.Use the loop output to decide whether the issue is unreachable, patched, or still unproven.

How to explain loops to leadership

Loops are not extra findings. They are the reasoning audit trail for hard decisions. A loop shows how GENESIS moved from "this might be vulnerable" to a more precise statement such as "this route is reachable, the source path is plausible, but proof still needs a browser replay." That makes the tool easier to trust because important decisions are visible rather than hidden inside a single model answer.

9. Orchestration Logic

The orchestrator is the control logic that keeps the scan coherent. It decides what context the AI sees, what tools can be used, how results are stored, and when the session is allowed to stop.

LogicWhat it doesHuman-readable reason
Prompt assemblyBuilds the AI instructions using target, profile, tool registry, memory, and recent progress.Keeps the agent aware of its mission and current evidence.
Role routingRoutes different jobs to assigned models, such as primary, critic, validator, or judge.Lets expensive models focus on hard reasoning and cheaper models handle volume.
Tool dispatchSends tool calls to the MCP server, waits for results, and stores outputs.Separates AI planning from controlled tool execution.
Hypothesis journalStores active, confirmed, and ruled-out hypotheses.Prevents the agent from forgetting why it ran a test.
Evidence enforcementDowngrades confirmed claims that lack concrete evidence.Protects the report from unsupported model assertions.
Loop guardDetects repeated identical tool calls and nudges the agent to pivot or finish.Stops the scan from getting stuck in circles.
Coverage gateBlocks early termination until enough attack classes or kill-chain areas were explored.Prevents shallow scans from looking complete.
Idle stopAllows the session to stop after repeated rounds with no new progress.Stops spending when the agent runs out of useful ideas.
FinalizationBuilds surface graphs, promotes eligible validated candidates, finalizes goals, and updates performance memory.Turns raw session activity into reportable state.

The repeated decision cycle

Cycle stepPlain-English actionTypical output
ObserveRead the latest target facts, tool results, candidate list, and unfinished goals.Updated session state.
ChooseSelect one next action that moves the scan forward.Tool call, hypothesis, validator task, or proof plan.
ExecuteRun the chosen tool through the controlled MCP layer or record a structured reasoning item.Tool output, event, error, or saved thought.
ExtractTurn useful output into endpoints, artifacts, candidates, evidence, or graph nodes.Structured records instead of loose text.
ChallengeAsk validators, critics, or loops to test whether the claim still holds.Support, refute, disputed, or needs-proof verdict.
DecidePromote, keep as candidate, rule out, dedup, or ask for one more proof.Cleaner report state.
Why findings can appear minutes later: raw tool output may arrive early, but GENESIS still needs enough concrete evidence and critic review before it should be treated as a finding. Optional validation-lab proof work may continue after the main finding is visible.

Promotion rules in plain English

RuleMeaning
Strict promotion is opt-in.Candidates need proof or auditable operator validation only when the operator uses the Validation Lab promotion path.

11. Fallbacks and Reliability Controls

GENESIS includes fallback behavior because AI scans are long-running and tool-heavy. The platform expects timeouts, model rate limits, parser quirks, target errors, and partial evidence.

Fallback or guardWhat happensWhy it matters
Tool failure captureTool errors are recorded and shown as session errors or tool outputs.A failed tool should explain itself instead of silently disappearing.
Model role fallbackIf no model profile is assigned, roles fall back to the configured primary model.Existing installs keep working without complex model setup.
Rate-limit backoffSub-agent calls can wait and retry instead of immediately failing the session.Protects long scans from temporary provider limits.
Evidence downgradeClaims marked confirmed without evidence are demoted to unverified or disputed.Keeps confidence honest.
Blind-bug proof requirementBlind SSRF, XXE, time-based SQLi, and similar classes need callbacks or passing oracles.Prevents "maybe it worked" reports.
Loop-breakerRepeated identical tool calls trigger a pivot-or-wrap-up nudge.Saves time and cost.
Wall-clock floorsExhaustive and Deep Research can refuse early final reports.Prevents the agent from ending before enough coverage exists.
Coverage checklistImportant attack classes must be touched before some profiles complete.Improves consistency across runs.
Candidate preservationUnproven ideas stay in Candidates instead of being lost.Humans can revisit leads without treating them as final findings.
Complete Validation jobStopped or completed sessions can continue proof and promotion for existing candidates only.Protects demos and long scans from losing value when discovery is stopped early.
Proof planner fallbackWhen a candidate lacks concrete proof parameters, the proof planner tries to create one safe deterministic proof action.Turns vague leads into executable validation work without silently confirming them.
Patched-control benchmarkRunning against a fixed twin checks whether high/critical findings disappear.Builds trust that the tool is not just noisy.

Common fallback outcomes

SituationGENESIS responseWhat it means for the report
Target is temporarily unreachableRecord error, retry when the profile allows, and preserve known state.Findings may be incomplete; note availability as a limitation.
Model provider rejects a requestUse configured fallback routing or mark the agent turn as failed.Check Errors and Costs before trusting scan completeness.
Validator says "needs proof"Send the candidate to optional proof orchestration.The candidate may need more evidence, but it does not block separately saved findings.
Stopped session has candidates needing proofRun Complete Validation only if you want proof runs and promotion records for candidate leads.The normal Findings tab should still be reviewed for saved findings.
Endpoint proof passes but source mapping is missingPromote based on live proof, with source mapping marked unknown.The finding is still useful; remediation may need human code lookup.
Source proof passes but live replay failsKeep source-only status unless live reachability is not required.Useful for engineering review, weaker for executive risk claims.
Duplicate candidates appearCluster them by endpoint, root cause, proof behavior, and likely fix.Report one canonical finding with merged evidence.
Patched twin still shows the issueTreat it as either residual vulnerability or false-positive warning.Do not use the metric as clean proof until reviewed.

13. Benchmark and Demo Methodology

The strongest executive demo is not a vague claim that GENESIS finds every bug. The strongest demo is a measured control: vulnerable target, patched twin, known ground truth, optional proof artifacts, and clear false-positive checks.

Demo objectRoleHow it should be reported
Vulnerable appThe target under test with planted safe vulnerabilities.Report recall: how many planted root causes GENESIS found.
Patched twinThe false-positive control with the same app after fixes.Report high/critical confirmed findings here as false positives or residual bugs.
Fake metadata serviceA safe proof canary for SSRF impact.Do not treat it as a normal vulnerable target; attach it as SSRF proof evidence.
Ground truth fileThe expected vulnerability list for the lab.Use it to calculate recall instead of guessing.
ScorecardThe measured result of a run.Show recall, proof coverage, duplicate rate, and patched-control false positives.
Recall. How many planted issues GENESIS found.
Precision proxy. Whether patched controls stay clean.
Proof coverage. How many confirmed issues have passing proof evidence.
Duplicate rate. How many raw leads collapse to the same root cause.
Time to value. How long until the first confirmed finding appears.
Cost per confirmed finding. How much model/tool spend produced validated output.

15. Scan Methodology Matrix

GENESIS has several scan styles because not every question needs the same level of effort. The right profile depends on whether the operator wants quick coverage, deep investigation, or proof-backed confidence.

ProfileBest forHow it behavesTradeoff
Standard or quick scanFast triage and early target understanding.Runs common recon and web checks, then saves evidence-reviewed findings.Fastest discovery, but fewer deep proof plans.
ExhaustiveBroad routine coverage across many bug classes.Pushes wider tool coverage and normal evidence-reviewed finding creation.More time and cost than quick scans.
Deep ResearchLong-horizon audits where hidden logic issues may matter.Allows more agent rounds, reasoning loops, memory use, uncommon test paths, and stronger evidence review.Best for depth, with higher runtime and cost.
Validated DynamicExecutive reporting and low-noise remediation queues.Adds hybrid preparation, optional validators, dedup, proof planning, and promotion scorecards.More context and proof artifacts, with normal findings still visible.

Endpoint-first versus repo-first reasoning

ApproachWhat it starts fromWhere it is strongWhere it needs help
Endpoint-firstLive services, URLs, APIs, forms, sessions, and observable behavior.Real deployed exposure, auth state, browser proof, OOB callbacks, and exploit-chain context.May miss bugs that require code-level lifetime, taint, or invariant reasoning.
Repo-firstSource code, commit history, call graphs, symbols, and component structure.Cross-file bugs, inconsistent patterns, patch reasoning, and source-level reachability.May overstate risk if the vulnerable path is not exposed in the deployed target.
HybridBoth live behavior and source/artifact context.Best path for proof-backed confidence: source explains why, endpoint proves exposure.Needs good mapping between endpoint, handler, source file, and proof oracle.
Recommended default: use Exhaustive for broad discovery, Deep Research for difficult targets, and Validated Dynamic when the scan should spend extra effort on hybrid mapping, proof planning, and executive scorecards. Candidates require proof or operator validation only when you use the optional promotion workflow.

19. GENESIS vs Traditional Security Tools

Leadership frequently asks: "We already have Nessus, Burp Suite, and a SAST tool — what does GENESIS add?" The answer is not that GENESIS replaces any single scanner. The difference is in how it reasons, validates, and reports.

CapabilityTraditional scannerGENESIS
Test strategyFixed checklist of known signatures run against the target.AI forms hypotheses, selects the right tool for each theory, and adapts based on results.
False positivesOften high — scanner flags anything that matches a pattern.Evidence checks, critic review, optional validation-lab proof, and patched-control comparison suppress unproven claims.
Logic-level bugsVery limited — tools test known patterns, not business logic.Reasoning loops, invariant tracking, and cross-file analysis find logic and design flaws.
Evidence qualityUsually a severity score and CVE number with no live proof.Confirmed findings need concrete evidence; blind bug classes still require callback hits, passing oracles, or human attestation.
Source + runtime correlationSAST and DAST are separate tools; findings are disconnected.Hybrid mapping links live endpoint behavior to source files and artifacts in one session.
Memory across sessionsEach scan starts from zero.Cross-session graph and vector memory carry findings, patterns, and technique recall forward.
Chained attack pathsTreats each finding in isolation.Attack graph connects vulnerabilities across services to show realistic exploitation chains.
Report noiseHundreds of raw alerts, most requiring manual triage.Candidates stay separate from confirmed findings; dedup clusters reduce the same root cause to one ticket.
Novel / zero-day style issuesCannot find what is not in the signature library.Open-ended reasoning and custom AI-written probes can test for classes of bugs, not just known CVEs.
ExplainabilityA score or CVE ID is the explanation.Every finding carries a hypothesis, evidence trail, reasoning loop, and proof record.
How to frame this for leadership: Think of traditional scanners as a fast metal detector at a security checkpoint. GENESIS is the follow-on investigator who picks up the flagged item, examines it, argues with a colleague about whether it is really dangerous, writes up confirmed cases, and files evidence — so that what reaches the team's desk is a prioritized, proven list rather than a pile of raw alarms.

Where traditional tools still win

ScenarioWhy a traditional tool may be preferred
Known-CVE patch auditingSignature scanners with CVE feeds (Nessus, Qualys) are fast, cheap, and purpose-built for asset-based CVE matching.
Compliance PCI/ISO checkbox scansStandard scanners produce outputs that auditors recognize; GENESIS output may need mapping to compliance controls.
Very large asset inventory scansFast network scanners (masscan, Shodan connectors) sweep thousands of IPs quickly; GENESIS is designed for deeper per-target work.
Lightweight CI/CD SAST gateSemgrep or Bandit as a CI pipeline check is simpler and cheaper for catching obvious patterns in code commits.

GENESIS is designed to sit above these tools — it can call them as sub-tools — while adding the reasoning, validation, and evidence layer that they do not provide on their own.

21. What a Confirmed Finding Looks Like

This section shows a representative example of a confirmed GENESIS finding so leadership and new readers understand exactly what reaches the remediation queue — and why every field matters.

Confirmed Finding
Unauthenticated IDOR — /api/v1/reports/{id} exposes any user's report
HIGH   Promoted
FieldValue
Attack classBroken Object Level Authorization (BOLA / IDOR)
Affected surfaceGET /api/v1/reports/{id} — authenticated endpoint, no ownership check
Root causeHandler queries by report_id from the URL without verifying that request.user.id == report.owner_id
HypothesisIf the numeric report ID is predictable, any authenticated user can retrieve another user's report by incrementing the ID.
Proof typeLive endpoint proof — HTTP request forge with substituted ID returned HTTP 200 and a different user's report body.
Proof evidenceRequest: GET /api/v1/reports/1042 as user B. Response: HTTP 200, report owned by user A (name, content confirmed different account). Screenshot saved to artifact store.
Validator verdictsEndpoint validator: support — live 200 response with cross-account data confirmed. Counter-validator: no refutation — no rate limiting, no ownership check found in handler source.
Source mappingbackend/app/api/routes/reports.py:88 — get_report() queries only by ID. No ownership assertion in the path.
Business impactAny authenticated user can read, enumerate, or exfiltrate reports belonging to other tenants.
RemediationAdd ownership check: if report.owner_id != current_user.id: raise HTTPException(403). Apply to all object-level endpoints using the same pattern.
CVSS estimate7.5 (High) — Network, Low complexity, Low privileges, No user interaction, High confidentiality impact
Dedup noteThree similar IDOR candidates on /invoices, /documents, and /comments clustered to this root cause — one fix addresses all four.

How to read this finding as a leader

Severity (HIGH) tells you priority. Critical = fix within 24 hours. High = fix within 1 sprint. Medium = fix within 1 quarter.
Proof evidence tells you it is real. This is not a scanner guess — a live HTTP request retrieved another user's data and a screenshot was saved.
Source mapping tells you where to fix it. The developer knows exactly which file and line to change.
Dedup note tells you the true blast radius. One architectural mistake caused four separate surface exposures — fix the pattern once, not four separate tickets.
Business impact tells you why it matters. Cross-tenant data exposure is a data breach risk — often a compliance and legal issue, not just a technical one.
Validator verdicts tell you it was challenged. A second AI tried to refute the finding and could not — so this is not an unchallenged claim.

Questions to ask before each engagement

Is testing authorized?
Written permission should exist for the target system. GENESIS should only be pointed at systems your organization owns or has explicit written authorization to test.
Is the target in scope?
Verify the target IP or domain matches the authorized scope. Confirm third-party services, CDNs, and shared infrastructure are excluded unless specifically authorized.
Is the data classification acceptable?
If the target handles PII, PHI, or payment data, confirm that AI API data handling agreements cover the classification before scanning.

GENESIS testing is non-destructive by design, but active scanning may trigger WAF alerts or briefly increase server load. Coordinate with operations for sensitive production systems.
Who reviews the findings?
Assign an owner for each confirmed finding before the scan starts. A finding without an owner is noise that will not be fixed.
How are credentials handled post-scan?
Rotate test credentials used during scanning. Do not reuse production credentials for GENESIS sessions.

Leadership FAQ — Questions Always Asked in a Briefing

QuestionDirect answer
How long does a typical scan take?Quick/Standard: 15–45 minutes. Exhaustive: 1–3 hours. Deep Research: 4–8+ hours. Deep Research on complex targets can run longer. All profiles validate findings after discovery, so final confirmed items may appear after the discovery phase completes.
How much does it cost to run?Cost depends on target complexity, scan profile, and model routing. A quick scan on a medium-complexity target typically consumes $2–$8 in AI API tokens. An Exhaustive run may use $15–$50. Deep Research on a large target can reach $80–$200. The Costs tab shows spend per session.
Can GENESIS damage our systems?No. GENESIS is designed as an assessment platform. It proves vulnerabilities exist without destructive actions — no files are deleted, no data is modified, no persistence is installed. Proof payloads run inside an isolated sandbox container. Active scanning may temporarily increase server load and may trigger WAF alerts.
Is it safe to run against production?With care. GENESIS scans are non-destructive, but active scanning sends real HTTP requests that could trigger security controls, increase load, or be logged. Recommended approach: test on staging first. For production, use a maintenance window and notify the ops team. Exclude critical write endpoints from scope.
What does a "false positive" rate look like?GENESIS uses evidence checks, critic review, optional proof artifacts, and patched-control benchmarks to minimize false positives. In benchmark runs against a patched control target, the goal is zero Critical/High confirmed findings. In practice, residual false positives exist and are classified per session. The benchmark scorecard shows precision per run.
What if GENESIS misses a vulnerability?No tool finds everything. GENESIS is designed for depth and proof-backed confirmation, not maximum recall from a short run. Deep Research mode and hybrid analysis improve coverage. Recall is measured in benchmarks. The correct framing is: "GENESIS found and proved X issues in this session" not "all issues are found."
Do we need internet access for scans?The GENESIS platform itself needs internet access only for the Anthropic API (Claude). The scan target can be internal-only. The OOB callback listener for blind vulnerability proof can be deployed internally — no public internet is required for the callback to work.
Who sees the findings data?Findings, tool outputs, and proof artifacts are stored in your self-hosted databases. Only your team with access to the GENESIS deployment sees the data. AI reasoning prompts are sent to Anthropic's API but do not include credentials or full database contents. See Section 22 for the full data residency breakdown.
Can we integrate findings into Jira / ticketing?GENESIS exposes a REST API (/api/v1/sessions, /vulnerabilities). Confirmed findings with CVSS, evidence, and remediation can be exported and pushed to any ticketing system via the API. Native Jira integration is on the post-go-live roadmap.
How is GENESIS different from running Burp Suite manually?Burp Suite requires a skilled operator to drive every test. GENESIS runs autonomously, forms its own hypotheses, selects tools, validates evidence with a second AI, and deduplicates findings — producing a prioritized, proof-backed list without manual intervention for each step. It also covers source code, binaries, and network simultaneously.
